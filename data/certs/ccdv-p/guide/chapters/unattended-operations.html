Key points

  • /goal needs a verifiable condition, /loop is session-scoped, and cloud scheduled tasks run without a local session.
  • --max-turns is unlimited by default and --max-budget-usd is an estimate that can overshoot and resets on resume.
  • --allowedTools preapproves calls but does not restrict the tool set, and non-bare -p runs load repo hooks and .mcp.json.
  • With --permission-prompts none, denials let the run continue, so verify completion with your own tests rather than Stop or the exit code.
  • Sessions persist the conversation, not the filesystem, and file checkpointing rewinds only Write, Edit, and NotebookEdit changes.

Unattended operation means a Claude Code run that nobody is watching: it starts from a goal, a schedule, or a repository event, and must finish, fail, or escalate on its own. claude -p exposes the Claude Code agent loop non-interactively, and the Agent SDK carries the same tools, agent loop, and context management in Python and TypeScript. Set spending and access limits, verify outcomes, and plan recovery and escalation before starting a run.

Trigger, bounds, and evidence

A trigger starts work on a goal, schedule, or event. A bound limits resources or permissions. Evidence records what happened, through output, session IDs, checkpoints, or hook events. Design all three together so a stopped run does not appear successful without verification.

Print mode is the entry point. claude -p 'prompt' runs non-interactively and can accept piped input. --output-format json returns the result and metadata, including the session ID, so persist it for correlation with logs. With --json-schema, check for structured_output, which is absent when a run ends without valid structured output, for example because Claude declined the request. --output-format stream-json --verbose --include-partial-messages emits newline-delimited event objects whose last line is a result message holding the final response text, cost, and session metadata.

Bounds: turns, money, and permissions

Print mode caps two resources. --max-turns 8 limits agentic turns; there is no limit by default, so an unbounded loop is the starting state. --max-budget-usd 2.00 limits estimated API spend for that invocation, and subagent spend counts toward it. Claude Code checks the cap against its own client-side cost estimate, which can differ from your bill, and spend can pass the cap, so leave headroom. On resume the cap resets its accounting: totals restored from earlier runs through --continue or --resume do not count toward it, so track the overall budget outside the CLI.

The permission mode sets the starting policy for what Claude may do without asking. --permission-mode accepts default, acceptEdits, plan, auto, dontAsk, bypassPermissions, or manual as an alias of default. --allowedTools preapproves matching calls; it does not restrict the available tool set. Use --tools to restrict available tools and configure permission rules separately. --permission-prompts none denies unresolved approval requests: anything that would prompt is denied unless a PermissionRequest hook allows it, Claude is told nobody can approve and not to retry, and the run continues. That last behavior is the trap most teams misread. A denial is not a failed run: the run can produce a polished report while every write and out-of-scope read was refused.

Control Bounds Does not bound
--max-turns 8 Agentic turns in print mode; default unlimited. Wall-clock time, per-turn cost
--max-budget-usd 2.00 Estimated API spend for the invocation, including subagents, with possible overshoot. Spend already spent before a resume.
--permission-mode, --allowedTools Permission policy and calls that run without a prompt. Available tools, credentials, or network reachability
--permission-prompts none Turns approval prompts into denials so the run continues. Whether the requested work actually happened

Give every unattended run a precise goal, an independent completion test, explicit scope, a wall-clock deadline, an estimated-cost cap, and a turn limit. Treat exhausted turns, denied permissions, missing evidence, failed verification, and timeout as distinct outcomes, and escalate each rather than reporting success.

Goals, schedules, and cloud tasks

A goal is a completion condition that directs repeated work. /goal adds a separate evaluator model that checks the condition after every turn, so completion is decided by a fresh model rather than the one doing the work. Setting a goal with -p runs the loop to completion in a single invocation, for example the documented runnable form claude -p '/goal All migrations compile and the test suite passes' --output-format stream-json --verbose. The goal clears when met, when the evaluator judges it impossible, or on an error requiring intervention; /goal clear clears it explicitly. Because the evaluator is a model, a met goal is an opinion, not a test result: run and inspect the tests yourself.

A session schedule repeats work within a Claude Code session. /loop 5m check the deploy repeats a prompt on a session timer. Session tasks are session-scoped: --resume or --continue restores tasks that have not expired, except those listed under Limitations, and recurring tasks expire seven days after creation, firing once more then deleting themselves.

A cloud scheduled task runs independently of a local session. It starts independent cloud sessions from a schedule, a GitHub event, or an API trigger. Two consequences matter operationally. Each repository you add is cloned on every run, and Claude starts from the repository's default branch unless your prompt specifies otherwise, so a run aimed at a failing revision must name it, or it will inspect different code. Documented GitHub trigger categories are pull requests, releases, and issues; there is no documented CI check-failure event. For an API-triggered task, configure the trigger on the web and store its task-scoped token as a secret. The supplied text arrives wrapped in a <routine-fire-payload> block that labels it as untrusted data and tells Claude not to follow instructions inside it unless the routine's own prompt says to, so the saved prompt must reference that block explicitly to use the alert. All connected MCP connectors are included by default and Claude can use them during a run, including writes, so remove every connector the task does not need.

Trigger State across runs Expiry and resume Best fit
/goal with -p One invocation; session history and filesystem are separate. Clears when met, judged impossible, or on an intervention-worthy error. Bounded "make this green" work
/loop session task Same session, session-scoped tasks. Restored on resume subject to limitations; recurring tasks expire after seven days. Periodic checks while a session lives
Cloud scheduled task Independent cloud session; repository cloned per run from the default branch unless the prompt says otherwise. Started by schedule, GitHub event, or bearer-authenticated API request. Recurring or alert-driven work with no local session
GitHub Action One Actions run per GitHub event. Bounded by workflow permissions and claude_args. CI/CD first response, PR handling

Event responders and CI first response

The Claude Code GitHub Action turns GitHub events into agent runs: anthropics/claude-code-action@v1 takes prompt, anthropic_api_key, github_token, settings, and claude_args, and a prompt invokes automation mode on any GitHub event. claude_args passes CLI options such as --max-turns and --allowedTools. For a plain-text prompt, Claude has no shell or GitHub API access until you grant the tools the prompt needs, with --allowedTools in claude_args or a permissions.allow rule in the settings input. The official setup installs the Claude GitHub App and its workflow examples grant id-token: write; grant the workflow only the permissions it needs and review Claude's changes before merging.

The following example targets trusted, same-repository CI revisions. Install the Claude GitHub App, set ANTHROPIC_API_KEY, put the workflow on the default branch, and replace CI with the upstream workflow name. It writes a diagnostic report to the job log; it does not fetch failed logs or post a comment. Do not use this privileged workflow on untrusted revisions: repository hooks or MCP configuration may execute with access to credentials.

name: CI failure first response
on:
  workflow_run:
    workflows: [CI]
    types: [completed]
jobs:
  investigate:
    if: >-
      github.event.workflow_run.conclusion == 'failure' &&
      github.event.workflow_run.head_repository.full_name == github.repository
    runs-on: ubuntu-latest
    timeout-minutes: 12
    permissions:
      contents: read
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          ref: ${{ github.event.workflow_run.head_sha }}
          fetch-depth: 1
          persist-credentials: false
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: >-
            Investigate likely causes of the failed CI run using the checked-out
            source. Report evidence, uncertainty, and next diagnostic steps.
            Do not modify files or perform remediation.
          claude_args: >-
            --max-turns 8 --max-budget-usd 2.00
            --permission-mode dontAsk --allowedTools "Read,Glob,Grep"

The three limits bind different resources: a 2 dollar estimated spend cap, eight turns, and a twelve-minute timeout. Pinning ref to github.event.workflow_run.head_sha selects the failed revision rather than the default-branch revision used by workflow_run. The repository filter does not establish that a revision is trusted; enforce trust before allowing this workflow to run. A production wrapper should fetch and sanitize logs with narrowly scoped credentials, persist the run URL and source SHA, validate the result, and notify on-call on timeout, denial, missing logs, or agent failure. Filter and authenticate upstream events, and review fork-code and secret exposure. Deduplicate by repository, workflow run ID, and attempt, bound concurrency, and record source SHA, event, session ID, and artifacts. Without failure evidence the responder cannot confirm a cause, so it should collect evidence, propose hypotheses, and name the next diagnostic step rather than claim a verified root cause. Require human approval for merge, production deploy, or irreversible remediation.

Checkpointing and recovery

Four mechanisms are commonly confused, and each restores something different. First: SDK session history persists the conversation, not the filesystem.

Mechanism What it restores Limits and caveats
--continue The most recent conversation in the current directory. Not files: persist session files and the workspace separately on ephemeral runners.
--resume <session-id> One identified local conversation. Restored spend from earlier runs does not count toward a new budget cap.
SDK file checkpointing Files changed through Write, Edit, and NotebookEdit, rewound to a prior state. Bash modifications and subagent edits have exclusions; rewinding files does not rewind the conversation or external effects.
Managed Agents sandbox checkpoint The full sandbox state, including filesystem, installed packages, and files the agent created, when a session goes idle. idle can coexist with an open workflow run, so inspect workflow state too; send a user.message to resume.

For later recovery, enable SDK file checkpointing and capture the session ID and turn-start user-message UUID. In Python, set enable_file_checkpointing=True and extra_args={"replay-user-messages": None} to receive UUIDs. Resume that session with checkpointing enabled and call ClaudeSDKClient.rewind_files(checkpoint_id) while connected. Each prompt that starts a turn is a checkpoint; its user-message UUID is the restore point. Check the rewind result for skipped paths.

Persist a checkpoint manifest, a recovery record for each run: incident key, source SHA, session ID, workspace snapshot or commit, phase, evidence, and cumulative spend. A session ID alone cannot restore the workspace or undo an external API action. In a recovery where a migration dies in phase 2 of 4, restore the workspace at its recorded snapshot, retrieve the persisted SDK session by ID, inspect whether phase 2's external operation completed, then resume with current evidence. If you must undo edits, use the captured checkpoint only within its documented scope; otherwise restore from version control or backups, and apply the remaining spend budget in your orchestrator rather than the CLI.

Notification, escalation, and termination

Hooks are configured handlers that run in response to lifecycle events. They can forward notifications to external services. Notification hooks forward events for side effects such as sending them to an external service; input includes session_id, transcript_path, cwd, message, an optional title, and notification_type, with matchers including permission_prompt and idle_prompt. Notification hooks do not block the events they forward. Stop runs when the main agent has finished responding; it does not run on user interrupt, and API errors fire StopFailure instead. Stop hooks also receive stop_hook_active, last_assistant_message, background_tasks, and session_crons, so check continuation state before treating Stop as completion, and avoid loops of your own making.

Route hook notifications through a controlled relay with deduplication, rate limits, and correlation IDs, and watch job status and expected artifacts independently: a response can finish with work pending. Escalate to an identified on-call owner for critical impact, ambiguity, missing access, repeated retries, or a missed deadline.

Termination needs its own plan. SIGTERM in print mode leaves the turn unfinished, terminates the process tree of any Bash command still running, then runs SessionEnd hooks and exits; use SIGINT or the SDK's interrupt() to end the turn first. On a remote MCP server a started job goes on after the print-mode process exits, so cancelling it is separate work. To stop a Managed Agents scheduled run, pause the deployment so no new scheduled run starts, interrupt the session, stop any open workflow runs, wait for idle, and archive or delete as appropriate; archiving ends a schedule permanently. Deleting a session is permanent and removes its record, events, and sandbox, so retain outputs first. On any cancellation: stop new triggers, interrupt, cancel remote work where supported, collect logs and checkpoints, revoke temporary credentials, remove ephemeral resources, and verify external state, because interruption and cleanup do not roll back effects.

Decision criteria

Pick the trigger from how the work ends, then set bounds from what the work can touch.

Situation Choose Evidence to check
A verifiable end state exists ("tests pass") and one session can hold the work /goal in print mode The evaluator's verdict plus your own independent test run
Periodic checking while a human session stays alive /loop session task Task not expired, not listed under Limitations
Recurring work that must run with no local session, on PR, release, or issue events Cloud scheduled task Clone revision (default branch unless the prompt says otherwise), removed connectors
Alerting system needs to start an engineering task now API-fired cloud task Returned session URL; payload referenced as untrusted data
Failure of a specific repository revision needs first response GitHub Action on workflow_run Checked-out head_sha, workflow permissions
Work must be rewound later SDK file checkpointing with captured UUIDs Whether edits came from Write, Edit, or NotebookEdit

Two rules generalize the table. Distinguish session-scoped scheduling from durable cloud scheduling before committing to either. Where incident scope is uncertain, prefer bounded least-privilege diagnostics with visible denials, independent verification, and human escalation over automation that can mutate the system.

Failure modes and recovery

A completed run can still leave the requested work unfinished.

Common mistake Treating exit 0 or a Stop hook as proof of success

Stop only means the main agent finished responding; it does not run on user interrupt and API errors fire StopFailure instead, so a green signal is not a verified incident resolution. Verify completion against your own test run and expected artifacts: background work can still be pending.

Common mistake Trusting --allowedTools as the security boundary

Without --bare, a -p session runs the hooks in a project's .claude/settings.json and connects the servers in its .mcp.json, even in a folder you have never trusted. Bare mode omits hooks even when explicitly passed through settings, so it is the wrong choice for a run that needs them. Keep command, credential, network, and destination restrictions outside the prompt, and review changes before merging.

Common mistake Assuming an unanswered approval blocks the run

With --permission-prompts none, anything that would prompt is denied, Claude is told nobody can approve and not to retry, and the run continues, so a denied run can look complete while whole parts of the investigation never happened. Surface denials explicitly and treat them as an incomplete result.

Recovery order when a run ends in a state you did not expect: stop new triggers, read the persisted result and session metadata, check workspace and external side effects, then choose between resume, rewind, and abandonment. Rewinding files does not rewind the conversation or external effects, and a remote MCP job continues on its own server.

Exam lens

Exam lenseditorial inference

  • Decision pattern: Given a completion condition, a periodic check, and a CI failure, select the goal loop for the condition, the session schedule for periodic work, and the event trigger for first response, and say why session-scoped tasks are not durable scheduling.
  • Decision pattern: For recovery after a crash, separate conversation history from supported file rewind, from managed sandbox checkpoints, from irreversible external effects.
  • Decision pattern: When a headless run finishes with a permission denied, the run continued after the denial, so mark the work incomplete and escalate rather than rerunning with looser permissions.
  • Decision pattern: For budgeting across resumes, restored spend does not count toward the cap, so overall budgeting belongs in the orchestrator.
  • Decision pattern: When assessing permissions, tool rules are not the credential and network boundary, and non-bare print runs load repository hooks and MCP settings.
