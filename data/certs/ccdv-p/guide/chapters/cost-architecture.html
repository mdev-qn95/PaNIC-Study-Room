  • Judge every choice on cost per successful task, not the per-token rate, because a failed attempt still bills its tokens.
  • input_tokens reports only the uncached tokens after the last breakpoint, so total input adds cache reads and cache writes.
  • A varying block such as a timestamp inside the cached prefix replaces cache reads with 1.25x writes on every turn.
  • Sweep output_config.effort on the current model before adding a second model; max_tokens is not a cost cap.
  • A tier spend cap returns HTTP 429 and a user-set org or workspace limit returns HTTP 400 invalid_request_error; do not retry either.

Cost architecture at scale is the way an organization shapes, routes, and meters Claude requests to control cost while meeting quality and latency targets. Repeatedly sending a growing conversation can make input-token use rise faster than the number of turns; prompt caching can reduce that repeated input cost. In Anthropic's production data, agent loops read a median 84% of input tokens from cache, and the top 10% read at least 94%. Model routing, effort tuning, batch processing, and per-tenant budgets are other cost levers. Output tokens cost five times base input tokens for the listed models.

Claude bills per token for input, cache writes, cache reads, and output. Above 100,000 prompt tokens, its per-token prices are five times higher across input, cache writes, cache reads, and output. Caching strategy and cache diagnostics

Prompt caching reuses the processed prefix of a prompt so repeated requests pay a cache-read rate instead of reprocessing input. The cache is a prefix match evaluated in strict order — tools, then system, then messages. Each breakpoint looks back at most 20 block positions for a prior cache write.

Choose the TTL by read pattern. A 5-minute write costs 1.25x base input and a 1-hour write costs 2x; read rates vary by model family. If a loop pauses for a person between turns, Anthropic recommends considering the 1-hour duration once about 1 turn in 20 follows a pause between 5 minutes and an hour, with few gaps longer than an hour.

Set breakpoints explicitly with "cache_control": {"type": "ephemeral", "ttl": "5m"} (or "1h") on a tool, system, or message content block. Automatic caching instead sets one top-level "cache_control": {"type": "ephemeral"}, which places a breakpoint on the last eligible cacheable block. When you mix TTLs in one request, 1-hour breakpoints must precede any 5-minute breakpoints. A prefix shorter than the model's minimum cacheable length is processed without caching and returns no error. The minimum varies by model; check the current prompt-caching table before relying on a threshold.

Read effectiveness from the usage object, not from the request. input_tokens reports only the uncached tokens after the last breakpoint, so total input equals cache_read_input_tokens + cache_creation_input_tokens + input_tokens. Cache diagnostics can compare a new request with the prior response and report the first point of divergence. Caching also affects throughput: cache_read_input_tokens do not count against default input-token (ITPM) rate limits, whereas input_tokens and cache_creation_input_tokens do.

Model routing and cascades

Model routing selects a model for each request and compares options by cost per completed task rather than per-token price. The output_config.effort setting controls response token use. Current defaults vary by model: Opus 5.5 and Haiku 5.5 default to medium; most other models default to high. Changing top-level effort mid-conversation can invalidate cached prefixes; hold it constant or use per-message effort where supported.

Do not use max_tokens as a cost cap. It is invisible to Claude, so lowering it does not make the model economize; a response that reaches the ceiling can be discarded and still billed. Set an output ceiling that fits the task, then tune output_config.effort against quality and cost.

A cascade concentrates higher-cost attempts on tasks that need them. When an outcome is verifiable, Anthropic recommends running every task at low effort and rerunning only failures at high effort. The same reasoning can apply across models: route tasks to a cheaper model first, then escalate verifier failures. The economics depend on how often the cheaper attempt fails and the cost of those failures.

Add a second model only after tuning the first. Sweep output_config.effort on your current model and build a pairing only if it beats that single model's whole curve of score against spend. Two patterns add a second model: an orchestrator fans out independent sub-contexts to cheaper workers, while the beta Advisor tool (advisor_20260301) lets an executor consult a stronger advisor mid-turn. Top-level usage omits advisor tokens because they bill at a different rate; usage.iterations[] itemizes executor and advisor sub-inference tokens.

Batch versus realtime economics

The Message Batches API charges 50% of standard prices for async work. High throughput and concurrent processing can make batches slightly overshoot a workspace spend limit.

For shared context, compare batch savings against cache hit rates and latency tolerance.

Fast mode (speed: "fast") offers up to 2.5x output throughput at premium prices. Fast mode is unavailable with the Batch API.

Pinning inference_geo: "us" on Claude 4.6-and-later models adds a 1.1x multiplier to every token category. Priority Tier capacity commitments are legacy and no longer sold; existing commitments remain usable through their contract end date.

Per-tenant budget enforcement

Workspaces organize API usage within an organization. The default limit is 100 workspaces per organization. When an organization reaches its tier spend cap, API usage pauses until the next month and requests return HTTP 429. A user-set organization or workspace spend limit returns HTTP 400 invalid_request_error. These spend-limit errors persist until access resumes; do not retry them as ordinary transient rate limits.

For attribution, the beta Usage and Cost Analytics API requires the analytics-usage-cost-2026-08-24 header. It supports up to five group_by[] dimensions per query. Cost amounts are decimal strings in cents with six decimals ("41280.000000" is $412.80 USD). The data typically refreshes within four hours and can take up to 24 hours. Late events may revise values until about seven days after month-end.

Because Analytics data lags, do not gate live traffic on it. For more than 100 tenants or strict caps, use Workspaces for tier and environment isolation and for cache and batch boundaries, and enforce per-tenant quotas in an application gateway: pre-check request size with count_tokens, meter usage and usage.iterations[] in real time, and reconcile daily against the Analytics /cost endpoint within its refresh lag. Workspaces alone hit three limits: the 100-active-workspace default cap, coarse monthly stops that surface as 400 invalid_request_error, and slight batch overshoots.

Decision criteria

Take the free wins before trading quality, and pick each lever from usage evidence rather than intuition.

  1. Enable prompt caching and keep prefixes byte-stable in tools to system to messages order.
  2. Trim dead input tokens: defer unused MCP tools, keep a few hot tools loaded, hand large files to code execution instead of pasting them into prompts, and compact before claude-haiku-5-5 reaches 100,000 tokens.
  3. Audit legacy prompts that force redundant verification steps on newer models.
  4. Move non-interactive workloads to the Message Batches API.
  5. Sweep single-model output_config.effort before adding a second model or a cascade.

Failure modes and recovery

Most cost incidents come from a broken cache prefix, a misread usage field, or retrying a limit that will not lift. The three traps below carry the highest blast radius.

Common mistake A varying block inside the cached prefix

Writes happen only at breakpoints, so putting a timestamp or the live user query at or before the breakpointed block forces a 1.25x cache write every turn with zero reads. Keep everything from tools through the last stable block byte-identical and place the breakpoint after it; use diagnostics.previous_message_id to find the first divergence.

Common mistake Reading input_tokens as the whole prompt

usage.input_tokens counts only the uncached tokens after the last breakpoint, which hides total prompt length, the Haiku 5.5 100,000-token cliff, and cache-write cost. Compute total input as cache_read_input_tokens + cache_creation_input_tokens + input_tokens and alert on that sum.

Common mistake Retrying a spend limit

A tier spend cap pauses requests with HTTP 429; a user-set org or workspace limit returns HTTP 400 invalid_request_error. Neither is a transient rate limit, so do not retry until access resumes. Do not retry them — abort, alert billing, and only then shift work.

Three further traps need explicit handling. max_tokens is a per-response output ceiling, not a complete task budget. Lowering it does not make Claude economize and can discard a response that still incurred token costs; tune effort and set an appropriate output ceiling. With the Advisor tool, do not price from top-level usage alone; it omits advisor tokens itemized in usage.iterations[].

Self-check

QA multi-turn agent on claude-haiku-5-5 caches a 95,000-token codebase prefix and appends 8,000 tokens of new tool outputs, then sees a sudden 5x cost jump even on cache-hit turns. Why, and what is the fix?Show answer
A

Total prompt length (cache_read_input_tokens + cache_creation_input_tokens + input_tokens = 103,000) crossed Haiku 5.5's 100,000-token threshold, which multiplies every token category, including cache reads and output, by 5x. Configure automatic compaction with a trigger below 100,000 minus the maximum per-turn growth (for example, 90,000).

QYou switch a cached multi-turn coding workflow from claude-opus-4-6 to claude-opus-5-5 and also toggle top-level output_config.effort from medium to high mid-conversation. Name two distinct cost impacts.Show answer
A

First, Claude 4.7-and-later models use a newer tokenizer producing about 30% more tokens for the same text, so raw counts rise; compare on cost per completed task and re-count with /v1/messages/count_tokens. Second, changing top-level output_config.effort mid-conversation can invalidate the prompt cache and re-bill the prefix as cache writes, so hold effort constant per session or set it per message where supported.

QWhy does a sudden drop in cache_read_input_tokens trigger HTTP 429 rate-limit errors even though requests-per-minute and total prompt sizes are unchanged?Show answer
A

Under cache-aware ITPM accounting, cache_read_input_tokens do not count toward ITPM, whereas cache_creation_input_tokens and uncached input_tokens do. A cache break converts zero-ITPM reads into full-ITPM cache writes, exhausting the ITPM bucket.
