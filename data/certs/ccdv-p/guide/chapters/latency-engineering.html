Key points

  • TTFT, TTLT, and OTPS are distinct measurements, so publish a first-response target and a completion target separately.
  • Streaming changes when output becomes visible, not how fast it is generated; caching targets TTFT and has no effect on output generation.
  • Put the cache checkpoint after the last identical block; a changing timestamp or query prevents an exact prefix match.
  • Run independent tool_use blocks concurrently, then return every tool_result in one user message before any text.
  • Fine-grained tool streaming skips server-side buffering and validation, so accumulate fragments and validate before dispatch.

Latency engineering means measuring a task's elapsed time and choosing changes that meet a latency target. Time to first token (TTFT) measures the wait for the model's first response; time to last token (TTLT) measures the wait for its complete response; output tokens per second (OTPS) measures the generation rate between them. Set separate service-level objectives (SLOs), or measurable service targets, for the first user-visible response and task completion.

How latency decomposes

Anthropic defines the three metrics precisely: TTFT is how long it takes to see any response from the model, TTLT is how long it takes to get the entire final response, and OTPS is the rate at which the response is generated between the two. The same guide models task latency as approximately calls × TTFT + output tokens ÷ OTPS + additional client- or server-side latency. Read that formula as a decision table: only the terms you can actually influence are worth tuning. Prompt size feeds the first term, because "the fewer tokens the model has to process and generate, the faster the response will be." Generation rate feeds the second term, which is where model choice and fast mode act. Tool duration and orchestration gaps feed the last term, which no API parameter shortens for you.

Track latency percentiles such as p95, the value at or below which 95% of observations fall. Keep successful and failed requests in separate series; their latency distributions can differ. Include gateway queue time in the user-facing measurement. Propagate deadlines to downstream work so it can stop when the caller's budget expires.

For an agent loop, decompose the end-to-end span into admission and queue wait, each Claude call's TTFT, model generation, each tool's execution, network and serialization, and application rendering. Record per-span timings and task-level percentiles; a single API duration cannot tell you whether a target missed because of first response, long generation, a serial tool chain, or one tailing tool. Treat failed calls separately, but include their duration in service health.

The critical path is the longest chain of dependent work determining completion. For a simple fan-out with no overlap or scheduling overhead, it includes sequential model calls and the longest branch of each parallel batch. If three independent lookups start together and take 180, 420, and 260 ms, the join waits about 420 ms. Measure end-to-end p95 directly; adding component averages or percentiles does not establish it.

Streaming and the first-token metric

Streaming delivers a response incrementally. Set "stream": true on a Messages request to receive it as server-sent events (SSE). A normal stream starts with message_start; each content block has a start, zero or more delta events, and a stop; one or more message_delta events and message_stop follow. Handle ping and error events as well, and tolerate unknown future event types.

Streaming can improve perceived responsiveness by showing output before it is complete. Do not assume streaming increases OTPS or meets a completion target. Track the first user-visible content separately from the first protocol event and from completion: tool input or thinking may arrive before visible text.

Fine-grained tool streaming extends this to tool arguments: set eager_input_streaming: true on a user-defined tool and enable request streaming, and the API exposes fragments of the tool input earlier by skipping server-side buffering and validation. The cost is that "you might receive partial or invalid JSON. A response that ends with the stop reason max_tokens can also cut a parameter off midway." Accumulate the fragments and validate the completed object before dispatch. Never let partial JSON trigger a non-idempotent side effect.

Parallel tool execution

Claude may return several tool_use blocks in one assistant response, and the application chooses whether to execute them concurrently, sequentially, or in a mix. Independent read-only calls are the safe fan-out candidates. Execute each call using its own id, then post one user message containing one tool_result block per call: "return one tool_result for each tool_use block, all together in the next user message. Match each result to its call with tool_use_id, and put every tool_result block before any text content in that message."

To cap the fan-out at the API, set "disable_parallel_tool_use": true inside tool_choice. With the default auto type, Claude calls at most one tool per response. With any or tool, it calls exactly one; some models do not support these forced-choice types.

Parallelize only independent operations. Serialize writes, calls that share mutable state, and calls where one result feeds the next. Bound concurrency so a single agent turn cannot saturate the tool service, the connection pool, or your rate limits: more simultaneous tools shortens the critical path while raising contention and tail risk.

Cache checkpointing

A cache breakpoint marks the end of a prompt prefix eligible for caching. Place cache_control on the last block whose prefix is identical across requests that should share it. A changing timestamp or query prevents an exact match at a later breakpoint. An earlier written prefix may still hit within the lookback window; otherwise the request misses. You can define up to four breakpoints for sections that change at different rates.

Two facts bound the payoff. Fewer input tokens to process reduce prefill work, and a cache hit avoids reprocessing a repeated prefix, so caching targets TTFT. But "prompt caching has no effect on output token generation. The response you receive is identical to what you would get if prompt caching were not used." Caching a 24k-token prompt will not make a 2,000-token answer generate faster.

Set the TTL deliberately. ttl accepts "5m" or "1h" and defaults to "5m"; a 1-hour cache write costs twice the base input-token price. The lifetime "is measured from the start of the request that writes or reads the cache entry, not from the end of its response," so a long streaming response consumes part of the window you just paid for. For an agent run with gaps longer than five minutes, compare the write premium against expected reuse before switching to the 1-hour TTL.

Keep stable content before the variable suffix. Cache prefix order is tools, system, then messages; put the checkpoint after the reusable portion in that order. Avoid placing secrets in cached content. Measure cache reads rather than assuming every request hits.

Effort, model choice, and capacity tiers

Effort controls how much work Claude puts into a response. Set output_config.effort on the request; otherwise the model's default applies. For Opus 5.5, adaptive thinking is always on and effort controls reasoning depth and cost. Lower effort can reduce latency and cost at the expense of quality; measure that trade-off on representative tasks. Levels, defaults, and calibration differ by model, so repeat the quality and latency sweep after a model change.

Model choice moves both prefill and generation. Current positioning and relative latency:

Model Documented positioning Comparative latency
Haiku 5.5 High-volume, latency-sensitive classification, extraction, routing Fastest
Sonnet 5.5 Best combination of speed and intelligence Fast

For speed-critical applications "Claude Haiku 5.5 offers the fastest response times while maintaining high intelligence." Select on a representative-workload eval, not on the family name: the right answer is the fastest model that passes your quality bar.

Fast mode uses a faster inference configuration on supported models. Anthropic documents up to 2.5 times standard OTPS, with benefits focused on OTPS rather than TTFT. On the Claude API, requesting speed: "fast" on an unsupported model returns an error; exceeding fast mode's limits or capacity returns a 429 or 529. On Microsoft Foundry, use a fast-mode deployment instead of the speed field. Consider fast mode when generation dominates the wait, and measure the result.

Priority Tier is a service-tier arrangement: "The API prioritizes requests in this tier over all other requests. This prioritization helps minimize 'server overloaded' errors, even during peak times." It is availability and queue protection, not a generation-speed control, and "Priority Tier capacity commitments are no longer available for purchase. Working against a target

The scenario: a support agent has a 4.0-second p95 target for a complete answer and a 0.8-second p95 target for visible first response. It runs Sonnet 5.5 with a 24k-token prompt, two independent MCP lookups, then a synthesis call. Assume the first call streams a user-visible acknowledgment before requesting tools. The following numbers describe one illustrative trace, not p95 measurements or service guarantees.

Critical-path component Before Tuned estimate
Queue + Claude first response (TTFT) 0.90 s 0.55 s (stable 20k prefix cached; effort chosen by eval)
Parallel lookup join 0.70 s (serialized 0.42 + 0.28) 0.42 s (max of 0.42 and 0.28)
Follow-up Claude call TTFT 0.90 s 0.55 s
240 output tokens at measured OTPS 2.00 s at 120 OTPS 1.50 s at 160 OTPS
App, network, serialization overhead 0.35 s 0.25 s
Total task time 4.85 s 3.27 s

The tuned estimate is 2 × 0.55 + 0.42 + 240 ÷ 160 + 0.25 = 3.27 s, following the cookbook's approximate formula. Under the acknowledgment assumption, visible output starts near 0.55 s. Neither estimate proves a p95 target: measure first-visible and complete-task latency across requests, alongside cache reads and tool duration.

Decision criteria

Diagnose the objective before tuning a lever. High TTFT points at queues, model and prompt prefill, cache misses, or reasoning before the first visible token; high TTLT with an acceptable TTFT points at output volume, low OTPS, tool duration, or extra round trips. A slow completion caused by long reasoning is not repaired by token streaming alone.

Symptom at p95 Evidence to inspect First lever
First visible response too slow Queue wait, prompt length, cache-hit rate, thinking before first token Cache checkpoint on the stable prefix; shorten the prompt
First token fine, completion late Output-token count, measured OTPS, reasoning volume Lower output_config.effort; fast mode where OTPS dominates
Many sequential round trips dominate Call count per task, tool dependencies in the trace Merge calls, parallelize independent tools
One slow tool in a fan-out Per-tool duration, join wait vs. max branch Bound and instrument the branch, not the model
Whole task too slow at acceptable quality Task success rate vs. latency by model Move to a faster model that still passes evals
Overloaded errors at peak, existing commitment 529 rate, tier assignment Priority Tier within the contract; it changes queuing, not speed

Prefer the least expensive, faster model and effort setting that passes task-specific quality checks. Lower effort can reduce thinking and tool-call verbosity, but if it causes omissions, retries, or extra agent turns, total latency rises. Evaluate the whole task — success rate, calls, tokens, p50/p95 — not one completion's raw token rate.

Failure modes and recovery

Common mistake Reporting TTFT as task latency

A first token at 0.6 s is not a 0.6 s task. TTFT, TTLT, and OTPS are three distinct measurements, and streaming changes the visibility of output rather than the rate of its generation. Publish both a first-response metric and a completion SLO, and label which one a tuning change moved.

Common mistake Executing partial tool input

Fine-grained tool streaming skips server-side buffering and validation, so early fragments can be partial or invalid JSON and a max_tokens stop can truncate a parameter mid-value. Buffer and validate before dispatch, and re-check the completed object against the tool schema before any side effect.

Common mistake Checkpointing after volatile content

A changing timestamp or query prevents an exact match at a later breakpoint; an earlier cached prefix may still hit through lookback. Check cache-read usage and move the breakpoint to the end of the reusable prefix if needed.

Measure the whole task, including queue wait, tool execution, retries, and orchestration gaps. When Claude returns parallel calls, send one matching result per call together in the next user message, before any text. Propagate the caller's deadline to downstream work. Reserve time for final synthesis, stop launching work after the deadline, and keep retries inside the same budget.

Assuming a cheaper or faster setting is universally better is the last common error: low effort, Haiku, fast mode, and Priority Tier each help under specific conditions and can hurt or be unavailable under others — quality regressions that add turns, unsupported models, and separate 429 or 529 capacity limits.

Exam lens

Exam lenseditorial inference

  • "Faster first visible response" means separate TTFT causes from output-throughput causes: streaming changes visibility, while prompt reduction, caching, model choice, and effort can move the first-token delay.
  • For independent tool_use blocks, consider concurrent execution and return all matching tool_result blocks in one user message; account for dependencies and safety before dispatch.
  • When total latency is dominated by many calls or tools, tune the critical path and reduce round trips — a higher OTPS mode cannot remove sequential dependencies.
  • For a repeated prefix that misses cache, inspect placement and cache-read usage; use the 1-hour TTL when reuse timing justifies its write premium.
  • Distinguish cached prefill from output generation: caching does not accelerate output-token generation.
