This appendix is a lookup table for the building blocks you choose between when you build with Claude: the Messages API, the Claude Agent SDK, Claude Managed Agents, Claude Code and its extensions, MCP, skills, subagents, hooks, plugins, and the cloud routes to the same models. Find the need you have, read its row, then check the enforcement table and the provider table before you commit. The documentation snapshot is 2026-11-19; capabilities and identifiers move, so verify the exact model and endpoint before you adopt a design.

Choose the execution owner and interface

The execution owner is the party that runs the agent loop, the tool calls, and the process around them; choose it before you choose any extension, because it fixes what you must build and operate yourself.

Three of these rows share one engine. The Agent SDK exposes the tools, agent loop, and context management that power Claude Code as a library in Python and TypeScript, the interactive product drives that same loop for a person at a terminal, and claude -p drives it once, non-interactively, for a script.

Managed Agents splits its configuration into named objects. An agent definition sets the model, system prompt, tools, MCP servers, and skills; you create the agent once and reference it by ID across sessions. The session then runs in an Anthropic-managed cloud sandbox or a self-hosted sandbox on your own infrastructure, so "managed" does not mean every sandbox is Anthropic-hosted. The offering is aimed at long-running tasks and asynchronous work, where the Messages API is aimed at custom agent loops and fine-grained control.

Select integrations and reusable instructions

An MCP server is a protocol integration that exposes external tools, APIs, and data to the agent. It complements the agent; it does not select the loop or the model. A local stdio server runs as a process on the host. Its access depends on that process's operating-system permissions and configured credentials. A remote HTTP server uses a network endpoint. HTTP servers are the recommended option for connecting to remote MCP servers, because that transport is the most widely supported for cloud-based services. In the configuration file, a JSON entry with a url but no type is a configuration error, because Claude Code reads an entry with no type as a stdio server.

An Agent Skill is a reusable procedure: instructions that load when used. Claude uses skills when relevant, or you invoke one directly with /skill-name. Custom commands have been merged into skills, and existing .claude/commands/ files keep working. A skill carries guidance, not credentials: access to an external system still needs an integration and its own authorization.

A subagent is a worker with its own context window, custom system prompt, specific tool access, and independent permissions. Reach for one when a side task would flood the parent's context or needs a narrower tool set. Give it an explicit task, the inputs it needs, and a return you can check; separate context alone is not an operating-system or credential boundary.

A plugin packages skills, agents, hooks, MCP servers, or other components as one directory that Claude Code installs and loads as a unit. A marketplace is a directory or repository with a .claude-plugin/marketplace.json file that lists plugins and where to fetch each one. These are three different objects: a catalog, an installed bundle, and a live MCP connection. Installing a plugin and connecting an MCP server are separate operations.

CLAUDE.md and a skill both hold instructions but answer different questions. CLAUDE.md files give Claude persistent instructions for a project, your personal workflow, or your entire organization, while a skill is an on-demand procedure that loads when relevant or when you call it by name. Put standing conventions in CLAUDE.md; put a repeatable procedure in a skill.

Where does this control get enforced?

A control is a mechanism intended to shape or restrict behavior. Some controls provide guidance; others can block a tool call or restrict a process. The mechanisms below sit at different layers, and their limits differ accordingly.

Mechanism Enforcement point Practical limit
Prompt, CLAUDE.md, skill The model receives instructions in context and decides how to act. Guidance is not an independent access boundary; do not rely on wording alone to enforce a prohibition.
PreToolUse hook Claude Code invokes the hook before the tool call, and exit status 2 blocks that pending call. PostToolUse happens after execution and shows stderr to Claude; the tool already ran. The hook must also be loaded: in bare mode a hook in ~/.claude/settings.json does not run.
Permission rule Allow rules let Claude Code use a specified tool without manual approval; ask rules prompt for confirmation; deny rules prevent use of a specified tool. Scope rules to the tools and actions you mean to govern; a rule about one path or tool is not protection against every other access route.
Managed setting Claude Code resolves an organization-set key over lower-precedence settings, and --model selects only from allowed models. Precedence secures the configuration value; the protection still depends on what that value controls and how the setting is deployed.
Sandbox The operating system enforces the boundary on the running Bash process, regardless of what the model chose to run or what an allowed command does. Check the filesystem and network policy, the exceptions, and which processes are actually sandboxed; this is not a machine-wide boundary by default.

The two hook facts are worth memorizing exactly. PreToolUse blocks a tool call that has not run yet; PostToolUse cannot undo a call that has. And a hook that is never loaded enforces nothing: bare mode still reads settings files and their permission rules, but a hook in ~/.claude/settings.json or an MCP server in the project's .mcp.json will not run.

Choose the provider route

The provider question has three parts: who operates inference, which credentials you present, and which identifier you put in the request. A billing relationship answers none of those by itself.

Route Operator, credentials, identifiers Feature considerations
First-party Claude API Anthropic. Authenticate with API keys, Workload Identity Federation, or App Attest. Direct platform baseline. Check feature-specific availability and account eligibility per model.
Claude Platform on AWS Anthropic operates it, unlike Amazon Bedrock where AWS operates the inference stack. AWS provides the authentication layer (SigV4 or API key), IAM-based access control, and billing through AWS Marketplace. Feature availability is typically same-day as the Claude API, subject to stated limitations.
Amazon Bedrock AWS operates the inference stack. Follows the Amazon Bedrock release schedule. Validate endpoint, region, model, beta, and tool support on that route.
Google Cloud, Anthropic managed The Claude API, run by Anthropic and reached through your Google Cloud project. The SDK client gets its token from Application Default Credentials (ADC). Claude API-style integration. Check the offering's supported and unsupported lists before migrating.
Google Cloud, Google managed Google-operated; the client SDK supports it through AnthropicVertex. The endpoint URL names the model, and in a cURL request you leave model out of the body. Some identifiers carry a date suffix, for example claude-haiku-4-5@20251001. Agent Skills, the MCP connector, and programmatic tool calling are listed as unsupported. That names server-side platform features, not behavior an independently hosted client cannot implement.
Microsoft Foundry Supports API keys and Entra ID tokens. Use the deployment name in requests, which is not necessarily the model ID. Check the deployment's hosting option, region, model, and feature support separately.

Provider migration is a contract migration. Map authentication method, endpoint shape, identifiers, and feature support, then test the actual path before you move production traffic. In particular, "Claude" in your cloud invoice does not tell you which company runs the inference: on Claude Platform on AWS Anthropic operates the inference stack, and on Amazon Bedrock AWS does.

Exact CLI and configuration details

  • Print mode: add -p (or --print) to any claude command to run it non-interactively. Output formats are text, JSON, and streaming JSON; the JSON form carries the result, session ID, and metadata.
  • Bare mode changes discovery, not everything: Claude Code still reads settings files and their permission rules, but a hook in ~/.claude/settings.json or an MCP server in the project's .mcp.json won't run. If a safety check depends on that hook, bare mode silently drops it.
  • Remote MCP entries need an explicit transport: a JSON entry with a url but no type is a configuration error, because an entry with no type is read as a stdio server. Prefer HTTP for remote servers.
  • Skills and commands: invoke a skill with /skill-name; custom commands are merged into skills, and existing .claude/commands/ files keep working.
  • Hooks: PreToolUse blocks the tool call; PostToolUse only shows stderr to Claude, because the tool already ran. Event semantics differ, so do not generalize exit behavior to every hook.
  • Google-managed requests: the client is AnthropicVertex, the endpoint URL names the model, and a cURL body omits model. Dated identifiers such as claude-haiku-4-5@20251001 can differ from first-party ones.
  • Foundry requests: pass the deployment name, not necessarily the model ID.

The following shell invocation is runnable with a configured current Claude Code installation and authentication; no specific SDK version is assumed.

claude -p "Summarize this project" --output-format json

The command prints structured JSON containing the result and session metadata. In CI, check the process exit status and validate the returned content before you use it downstream, and account for repository-loaded components and any chosen --bare mode.

Practitioner reasoning

Start by choosing who operates the loop and the runtime. A reusable skill or an MCP server does not answer whether your application owns retries, approval, the execution environment, and session lifecycle.

Choose manual tool orchestration when the business transaction needs explicit approval before side effects, or audit logging at each step; the tool runner exists to remove that loop code, and the manual loop is the documented choice for human-in-the-loop approval, custom logging, or conditional execution. A runner reduces loop code but not responsibility for external service permissions, idempotency, or result validation.

A remote MCP server centralizes integrations and adds a network and authentication boundary; a local stdio server keeps the process on the host but still inherits that process's credentials and filesystem access. Use least-privilege credentials and check the server's trustworthiness either way.

Treat a subagent as a context and tool-scope device, not as isolation: it gets its own context window, custom system prompt, specific tool access, and independent permissions, while an OS-enforced boundary is a different mechanism that applies to the running process.

Worked example

A team needs automated PR review of a Python service plus a human-approved deployment. Use the GitHub Actions integration for the review trigger, since it responds to @claude mentions in issues and PR comments, a project skill for the review criteria, since Claude loads a skill when relevant or on explicit invocation, and a read-only MCP integration for the issue tracker, because MCP is what reaches external tools and APIs. Constrain what the agent may run with permission rules, where deny rules prevent use of the specified tool, and with a PreToolUse check that blocks the pending call. Enforce filesystem and network boundaries in the execution environment, where the operating system applies the sandbox boundary to the running process. Put deployment authorization in the deployment system and keep the deploy itself outside the review workflow; that arrangement is an architectural illustration, not a claim that a prompt enforces approval.

Common mistakes

Common mistake Believing a post-tool hook stopped the action

PostToolUse reports after the tool already ran, so exit status 2 there cannot prevent that call; only PreToolUse blocks the pending one. Assuming a pre-tool hook runs everywhere is the mirror error: in bare mode a hook in ~/.claude/settings.json does not run.

Common mistake Conflating a marketplace, a plugin, and a live MCP server

A marketplace is a catalog with a .claude-plugin/marketplace.json file, a plugin is a bundle of components installed as one unit, and an MCP server is a running integration that supplies tools, databases, and APIs. Installing one is not starting another.

Common mistake Reading a cloud name as an operator

Claude Platform on AWS is Anthropic-operated; Amazon Bedrock is AWS-operated. The two Google Cloud offerings likewise differ in who operates them.

Common mistake Carrying identifiers across providers unchanged

Foundry requests take the deployment name, which is not necessarily the model ID, and Google-managed listings use dated identifiers such as claude-haiku-4-5@20251001.

Version caveats

Version check · 2026-11-19

Feature matrices, regional availability, current identifiers, and deprecation dates move, and provider identifiers already differ, for example the dated claude-haiku-4-5@20251001. The Google-managed exclusions cited here, Agent Skills, the MCP connector, and programmatic tool calling, are that offering's list; do not generalize it to every Google Cloud service. Verify the exact endpoint and deployment in the provider's own documentation before implementing, and inspect the actual environment for which sandbox settings and hooks are deployed rather than assuming them.

Exam lens

Exam lenseditorial inference

A scenario that requires a fully customized approval sequence points toward a manual loop; one that requires an embedded agent with built-in tools points toward the Agent SDK. A long-running asynchronous task on managed infrastructure points toward Managed Agents, and its self-hosted sandbox option is not a requirement to build the loop yourself. Separate behavioral guidance from mechanisms that can block a tool call or enforce an OS boundary. When a scenario migrates clouds, distinguish who operates inference, the credentials, the model or deployment identifiers, and the feature list.
