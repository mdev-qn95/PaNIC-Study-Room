Key points

  • Release protocol revision, transport, endpoint, credentials, tool catalog, model, prompt, and route as one tested bundle, and roll back the whole bundle.
  • 2025-11-25 negotiated version and capabilities in initialize; under 2026-07-28 each request carries them in _meta.
  • A tool list that changes between requests counts as a prefix edit and can return 400 on Claude Fable 5.2.
  • Under the 2025 authorization profile, invalid or expired tokens return 401, and the server must not pass the client's token downstream.
  • The Messages API connector needs a public HTTPS endpoint, cannot reach a local stdio server, supports tool calls only, and is not ZDR-eligible.

Model Context Protocol (MCP) connects clients to tools and other context supplied by servers. Its 2026-07-28 revision uses a stateless request/response core. Production change management tracks the dependencies a request uses: protocol revision, transport, endpoint, credentials, tool catalog, model, prompt, and route. These layers can change independently. For example, on Claude Fable 5.2, changing a tool list between requests counts as an edit to the conversation prefix and can cause a 400 when earlier thinking blocks are sent back. Name the changed layer, test the new combination before routing traffic to it, and keep a tested release bundle for rollback.

The deployable contract

The deployable contract is the set of artifacts a running request depends on. Inventory it, version each part separately, and record the combination in a release manifest: protocol revision does not version your business tools, and a schema version does not version your route.

Layer Version it as Typical break on upgrade
MCP protocol revision Revision date (2025-11-25, 2026-07-28) List-change delivery differs by revision.
Transport Per endpoint (stdio, Streamable HTTP) The Messages API connector cannot reach a local stdio server.
Auth Canonical resource, issuer, scopes Under the 2025 authorization profile, invalid or expired tokens return 401.
Tool catalog Names, descriptions, input schemas Tool selection may change after a catalog update.
Model snapshot Model ID plus platform deployment Requests to retired models fail.
Prompt and route Release ID or content hash, gateway route Some mid-conversation edits trigger prefix checks and 400 errors under model-specific defaults.

Remote MCP deployment and authentication

The protocol revision decides how versions and capabilities are agreed, which decides what a client must do on an upgrade. The published MCP revision is 2026-07-28. Keep 2025-11-25 in view as a handshake-era compatibility target, not an alias for the new wire behavior.

Aspect 2025-11-25 2026-07-28
Version agreement Client MUST send a supported protocol version in initialize. The server MUST respond with the same version if it supports it. The client SHOULD disconnect if it cannot support the returned version. Each request travels on its own and carries protocol version, client identity, and client capabilities in _meta.

The standard transports are stdio and Streamable HTTP. Streamable HTTP replaced the HTTP+SSE transport from protocol version 2024-11-05. Claude Code deprecates the legacy SSE transport and recommends HTTP servers where available. Streamable HTTP can still use SSE to stream server messages.

Authorization is optional in MCP. For HTTP implementations that support authorization, the 2025 specification recommends this profile; its requirements apply when the profile is used.

Requirement Rule
Authorization server MUST implement OAuth 2.1 with appropriate security measures for confidential and public clients.
Resource metadata Servers MUST publish OAuth 2.0 Protected Resource Metadata (RFC 9728), and clients MUST use it for authorization-server discovery.
Token audience Clients MUST implement Resource Indicators (RFC 8707) to specify the target resource of each token request.
Server validation Servers MUST accept only tokens valid for their own resources and MUST NOT accept or transit other tokens.
Downstream calls The MCP server MUST NOT pass through the client's token; obtain a separate appropriate downstream credential.
Rejection Invalid or expired tokens MUST receive HTTP 401.
Stdio Implementations SHOULD NOT follow this profile and instead retrieve credentials from the environment.

The canonical resource identifies the target resource for a token. When a hostname or path change also changes that identity, treat it as an authentication migration: publish correct metadata, obtain a token for the new resource, validate issuer and audience at each replica, and test expired, wrong-audience, and insufficient-scope cases. Do not clear a 401 by forwarding a token meant for another backend.

Claude Code scope is deployed configuration: the effective server can differ between developers, or between a laptop and CI, on an identical repository. Keep bearer secrets out of the committed .mcp.json.

Scope Where it lives Who sees it
local (default) Only the project where you added the server Private to you.
project .mcp.json at the project root Shared with the team.
user ~/.claude.json Every project on your machine, private to your account.

Use --scope project to store this server in project scope. Claude Code documents the claude mcp add command and --scope project option.

# --scope user selects user scope; omitting scope selects local.
claude mcp add --transport http shared-server --scope project https://example.com/mcp

Tool and schema versioning

An MCP tool has a name and schema metadata; a description can explain its purpose. A tool catalog change alters the definitions available to the client. Delivery depends on the protocol revision. A server using the handshake-era protocol that declared listChanged SHOULD send notifications/tools/list_changed when its tool list changes. Under 2026-07-28, list-change and resource-update notifications arrive only on a subscriptions/listen stream the client opened. Re-list after change events, invalidate dependent caches, and test missed events, reconnects, and catalog reconciliation.

Change Breaking? Migration move
Remove or rename a tool Yes Publish v2, keep v1, drain traffic, then retire v1
Require a formerly optional argument Yes Accept both signatures during the overlap
Narrow an enum or change units Yes New tool name or explicit schema version
Change what a result means Yes New tool; the old description now misleads the model
Add a tool or an optional input Possibly Re-evaluate selection and behavior before rollout

Retain v1 alongside v2, compare real calls and results, migrate client allowlists, and retire v1 only after traffic drains. A notification is a cache invalidation signal, not a compatibility promise.

The Messages API connector

The Messages API MCP connector reaches remote MCP servers through a public HTTP endpoint. It supports Streamable HTTP and SSE, but it cannot connect directly to a local stdio server. The connector currently supports only MCP tool calls. It is not eligible for zero-data-retention (ZDR) arrangements; exchanged data follows the feature's standard retention policy.

Connector migration changes request configuration. The mcp-client-2025-11-20 beta header replaces deprecated mcp-client-2025-04-04. Tool configuration now lives in MCPToolset objects in the tools array. Each mcp_servers entry uses type: "url", url, and name, with optional authorization_token. Its URL must start with https://. An mcp_toolset entry refers to the server through mcp_server_name. For an allowlist, set default_config.enabled to false and enable approved tool names under configs. This controls exposure through the application and does not replace server-side authorization. Keep tool definitions stable within a conversation, and test catalog changes against the target model before routing production traffic to them. On platforms that support mcp-client-2026-09-15, the connector can record and pin a server’s tool list. Return the assistant message unchanged, including mcp_tool_listing blocks, and keep the beta header on requests carrying those blocks; later requests reuse the recorded list. Pinning the list does not freeze the server’s implementation, so retain compatible server behavior as well.

Model and prompt versioning

Model IDs have a lifecycle, and alias behavior depends on the generation. On the Claude API, shorter aliases for pre-4.6 models such as claude-sonnet-4-5 point to the latest dated snapshot for that minor version. From the 4.6 generation, a dateless ID maps to one fixed snapshot. Pinning a model ID does not freeze observable behavior: infrastructure updates can produce minor differences even when the ID and weights stay the same. Requests to retired models fail, so migrate before retirement. Google managed Claude and Amazon Bedrock set their own retirement schedules.

Prefix rules can turn tool changes into model errors. For Claude Fable 5.2 thinking blocks, a tool list that changes between requests counts as an edit. For Claude Fable 5.2, editing system, tools, or earlier messages and then returning affected thinking blocks fails the prefix check; by default, the request returns HTTP 400. A beta setting can instead drop affected blocks, losing that reasoning; treat it as a temporary recovery and measure its effects. Claude Fable 5.1 cannot read Claude Fable 5.2 thinking blocks. On the Claude API and Google-managed Claude on Google Cloud, a switch drops incompatible blocks and continues without that reasoning. Parameter support also varies by model: Claude Opus 5 accepts tool_choice values any and tool, and Claude Fable 5.2 rejects both.

Prompt versioning follows the same discipline as code. Keep templates, variables, system text, and example sets in version control with a content hash or release ID, logged alongside model ID, tool schema digest, platform, gateway route, and eval dataset revision, and keep secrets out of telemetry. A prompt edit is a release that can invalidate preserved thinking-prefix assumptions: start new conversations on the new manifest or follow the documented migration procedure. Anthropic's updates to the Claude consumer app system prompt do not apply to the Claude API.

The same model can require different request identifiers or deployment configuration by platform; a gateway can hide those differences from callers, but the adapter still has to handle them.

Platform Identifier in requests

Amazon Bedrock global.anthropic.claude-fable-5-2 or us.anthropic.claude-fable-5-2, served only by the bedrock-runtime endpoint.
Microsoft Foundry The deployment name, which is not necessarily the model ID.
Foundry Anthropic-hosted fast mode A claude-fable-5-2-fast deployment, with speed omitted.

Claude Code points at a gateway with ANTHROPIC_BASE_URL. Configure gateway authentication and its upstream provider separately. Changing the base URL alone does not establish identical model names, capabilities, or entitlements.

When using a gateway, inventory its authentication, quotas, logging, model mapping, and routing behavior. Test semantic translations because the gateway becomes another dependency. Keep a tested matrix per upstream (deployment ID, region, identity, quota, beta headers, tool and streaming support, data handling, retirement date, request and response shape, SDK adapter), then run the same contract and behavioral suite per path. Route only where the full combination is supported.

Migration testing against breaking changes

Migration testing compares the complete old and new request configurations on replayable, privacy-appropriate golden cases and multi-turn trajectories; model replacement is not an ID substitution. Measure task success, tool selection and argument validity, groundedness, refusal and stop outcomes, schema parsing, retries, p95 latency, and cost; include adversarial, boundary, and long-context cases; validate actual side effects in an isolated or simulated system rather than trusting response text; and set regression thresholds before you inspect results.

Test lane Proves
Request acceptance Parameter parity holds on the target model and platform
Auth Metadata discovery, audience validation, expiry, and scope failures behave correctly
Event delivery List-change and stream events reach the client after reconnect
Multi-turn continuation Prefix and thinking-block assumptions survive the new turn shape
Session rollback The prior manifest can still serve conversations already in flight

Progressive rollout with rollback

Roll out one change at a time where practical, assigning whole conversations rather than individual turns to a cohort. Keep a known-good bundle of model, prompt, tool schema, endpoint, and routing, and rehearse restoring it, including credentials and data compatibility.

Worked example (illustrative; these targets are not Anthropic requirements): a support agent runs 10,000 daily conversations on model A, prompt p17, and server orders-v1 with the old schema. A candidate adds an optional region and a separate refund_quote_v2 with different currency units. The manifest records exact versions, the tool-list hash, the OAuth resource, and the deployment; the server keeps v1 live and the toolset enables only approved tools.

Stage What runs Gate to advance
Offline replay 500 representative cases in a sandbox, since real and candidate calls would otherwise duplicate actions: malformed inputs, multi-turn tool use, bad audience, expired token, no-result behavior No unauthorized side effects, no contract failures, at most 1 percentage point decline in labeled task success
Canary 1% of new conversations, then 10%, 50%, 100% Quality, correctness, latency, errors, and spend pass; each cohort compared by customer and task type, because a low global error rate can hide a failing tenant
Rollback New conversations return to the prior manifest Existing candidate conversations stay on their compatible route or restart explicitly

Restore server, allowlist, and prompt together when any depends on the changed schema, and test the Fable 5.2-to-5.1 path because the older model cannot read newer thinking blocks.

Decision criteria

Choose the migration unit by asking what a running conversation depends on.

Question Choose Evidence
Do both ends speak the target revision? Protocol or transport change only when client and server support it, since version and capability handling differ between the handshake era and the per-request era. Contract test on the real pair
Did the resource identity move? Auth migration with metadata and token-audience work, because the canonical resource is part of the credential. Expired, wrong-audience, low-scope cases
Did tool meaning change? New tool name for changed meaning; reconcile notifications and test even additions. Side-by-side v1/v2 call diff
Did the model ID change? Full bundle swap after checking platform matrix, prefix rules, and parameter parity, since a fixed snapshot still can differ from the previous route. Golden-case replay per route
Is the canary good? Expand only on per-cohort results, not aggregate averages Per-tenant quality and error rates

Failure modes and recovery

Treat any change to one layer as part of the full release.

Common mistake Reverting only the model name

Rolling back the model ID while leaving the new prompt, tool schema, thinking history, or provider deployment in place keeps the mismatch that caused the failure. Restore the whole bundle.

Common mistake Reading a 401 as a broken tool

An invalid or expired MCP token returns HTTP 401 under the 2025 authorization profile. A Claude Fable 5.2 prefix violation returns HTTP 400 by default. These codes have other possible causes, so inspect the error details before deciding whether to fix identity, history, or the request. Avoid retrying an unchanged invalid request.

Common mistake Assuming the connector behaves like a client

The connector needs a public HTTP endpoint, cannot connect to local stdio directly, supports tool calls only, and is not eligible for ZDR arrangements. Check these constraints during design and deployment review.

Three assumptions fail quietly. A dateless model ID is not always a moving alias, and pinning an ID does not freeze serving behavior. The 2025 initialize negotiation and notification behavior do not apply unchanged to the 2026 revision. Deprecating legacy HTTP+SSE does not prohibit SSE streaming inside Streamable HTTP. Gateway routing does not make vendor APIs or retention guarantees interchangeable. A secondary route may also be retired or lack a required capability.

Exam lens

Exam lenseditorial inference

These are editorial decision patterns, not exam questions.

  • A server upgrade changes its tool list and a long conversation starts failing with 400: inspect model-specific prefix rules and the current tool definitions before changing OAuth settings.
  • A fallback route on Foundry or Bedrock rejects the same request: inspect deployment IDs, provider-specific parameters, capabilities, beta headers, and lifecycle before retrying.
  • A migration changes the MCP URL and the old token stops working: verify resource metadata and token audience instead of forwarding a downstream token.
  • A canary improves average quality but breaks one schema or customer cohort: stop expansion and roll back the compatible release bundle; aggregate performance alone is insufficient.
