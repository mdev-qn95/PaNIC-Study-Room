Key points

  • Limits are enforced in RPM, ITPM, and OTPM per model class, so the tightest dimension binds admitted work.
  • ITPM counts input_tokens plus cache_creation_input_tokens; OTPM counts tokens actually generated, so max_tokens costs no quota.
  • Classify every 429 from error.details.error_code and retry-after: rate and ramp limits recover with pacing, a tier spend cap does not.
  • Workspace caps and workspace-scoped keys limit traffic but reserve no capacity — organization-wide limits always apply.
  • Message Batches bill at 50 percent of standard prices, expire unfinished work after 24 hours, and must be joined by custom_id, not order.

The Claude API caps throughput in three independent dimensions, and the tightest one limits admitted work. Messages limits measure RPM (requests per minute), ITPM (input tokens per minute), and OTPM (output tokens per minute) per model class, so tracking requests alone misses token bottlenecks. Service-configured limits apply at the organization level on continuously replenished token buckets, so a comfortable per-minute average does not make a burst safe. Workspaces, shared model-family buckets, and Message Batches (the asynchronous API for grouping Messages requests) add separate ceilings that remain subject to shared pools rather than reserving dedicated capacity. Scaling means finding the binding constraint — rate limits, token throughput, or batch economics — then changing the plan and recalculating.

How Claude meters throughput

The Messages API enforces three rate-limit dimensions per model class, and exceeding any one returns HTTP 429 naming the exceeded limit.

Dimension What the API counts
RPM (requests per minute) Each request against the model's bucket.
ITPM (input tokens per minute) input_tokens plus cache_creation_input_tokens; cache_read_input_tokens are excluded.
OTPM (output tokens per minute) Tokens actually generated in real time; max_tokens does not factor into OTPM.

The API estimates ITPM at the start of each request and adjusts that estimate during the request to reflect actual input tokens used. Because OTPM counts only tokens actually produced, setting a higher max_tokens value incurs no rate-limit penalty.

Prompt caching raises effective input throughput: a request that reads 7,000 cached tokens, writes 2,000, and sends 1,000 uncached tokens consumes 3,000 ITPM rather than 10,000. A cache-miss surge therefore raises charged ITPM even when prompt length and request rate stay constant.

Buckets do not map one-to-one onto model names. Sonnet 4.6 and Sonnet 4.5 share one combined Sonnet 4.x bucket, while Sonnet 5.5 and Sonnet 5 each have a separate bucket. Inspect the current model and tier table and your own account limits before estimating capacity.

Read limits from the response headers

Responses report the enforced limit, current usage, and the next reset, so a gateway can name the constraining dimension. The four families are anthropic-ratelimit-requests-{limit,remaining,reset}, anthropic-ratelimit-input-tokens-{limit,remaining,reset}, anthropic-ratelimit-output-tokens-{limit,remaining,reset}, and anthropic-ratelimit-tokens-{limit,remaining,reset}. Reset timestamps use RFC 3339, and remaining token counts are rounded to the nearest thousand.

The aggregate family is easy to misread: anthropic-ratelimit-tokens-* reports the most restrictive limit currently in effect, not an extra budget on top of input and output. Use headers to name the binding limit and pace traffic, and reconcile them against your own usage accounting rather than treating rounded values as a precise ledger.

Bursts and ramp limits

Token buckets replenish capacity continuously rather than resetting on a fixed schedule, and the API can enforce limits over windows shorter than a minute. A rate of 60 RPM can be enforced as 1 request per second, so a short burst triggers 429s below the minute allowance.

A ramp limit caps how fast your organization's token usage on a model can grow. After a sharp increase in usage — a burst of requests within a few seconds can qualify — requests return 429 while ITPM and OTPM headroom remain. The permitted level is your highest per-minute usage in the recent past plus a step: each minute you may rise one step above that peak, and the ceiling stops at your rate limit. A ramp error is a rate_limit_error whose Messages API error.details.error_code is ramp_limit_exceeded. Message Batches are not subject to ramp limits.

Ramp limits meter input and output tokens separately, exclude cache reads, and use a step and starting amount that vary by model and can change. Increase traffic gradually after a deployment, cache cold start, or scheduled job rather than launching at full concurrency.

Spend caps and other 429s

A 429 is not one condition. Reaching the monthly tier spend cap also returns HTTP 429 with type rate_limit_error and error.details.error_code set to enforced_spend_limit_reached, with no retry-after header; SDK and application retries keep failing until access resumes. A spend limit you configure yourself returns HTTP 400 with invalid_request_error, except on the Claude Code workspace where over-limit requests can return 429 with retry-after.

Response Identifying signal Cause Action
429 rate limit Body names the exceeded limit; retry-after in seconds when present RPM, ITPM, or OTPM exhausted Wait the indicated seconds, add jitter, reduce admitted work
429 ramp limit error.details.error_code is ramp_limit_exceeded Growth rate, below steady-state ceilings Ramp up gradually; do not treat as a permanent ceiling
429 tier spend cap rate_limit_error, enforced_spend_limit_reached, no retry-after Monthly spend cap reached Stop retrying; fix budget or tier
400 spend limit invalid_request_error with a spend-limit message A limit you configured Raise it or route the work elsewhere

Queueing and backpressure

Use queues to control what reaches those counters. Bound queue length and age so a rate limit does not turn excess demand into growing latency. Run a distributed admission controller — a gateway component that meters and gates outbound calls — per organization, model bucket, and workspace. Have it track request count, estimated uncached input including likely cache writes, and projected output; reserve against each budget atomically, reconcile with observed usage, and bound in-flight output. Because Claude produces output over time, an output reservation is your safety policy, not the API's OTPM accounting rule. Count retries too: a retry storm consumes the budget you were waiting for.

Bound both queue length and queue age, then shed load upstream: when demand exceeds the sustainable drain rate, reject, drop, or return a retryable overload response. Measure queue wait separately from API latency, or a backlog looks like a slow model.

Prevent head-of-line blocking, where an oversized job at the front of a queue stalls smaller admissible jobs for unrelated tenants. Use size classes or bounded look-ahead, and let large jobs accumulate credit so they do not starve. Separate interactive and bulk classes, with aging or a reserved share so bulk work cannot starve interactive requests.

Multi-tenant quota and isolation

The API enforces service-configured limits at the organization level, and you can add user-configurable spend and rate limits per workspace. Organization-wide limits always apply, even when workspace limits add up to more than the organization has. A workspace cap limits traffic attributed to that workspace; it does not reserve capacity for it.

API keys can be scoped to a single workspace, limiting access to resources in that workspace, while unscoped keys select a workspace per request via the anthropic-workspace-id header. A workspace-scoped key limits resource access to that workspace, but does not create throughput the organization lacks.

Isolation mechanism What it gives you What it does not give you
Workspace custom rate and spend limits A per-workspace ceiling Capacity reserved against the organization
Workspace-scoped API key Access limited to one workspace A per-key throughput guarantee
Multiple API keys Separate credentials to manage Per-key caps — add gateway accounting or separate workspaces for tenant isolation
Weighted fair scheduling in your gateway Enforced tenant shares at your layer Any protection at the API when the organization bucket is full

Charge scheduling to both the tenant cap and the aggregate organization or model constraint, and let tenants borrow unused shares while billing estimated token work.

Batch pipeline design

Asynchronous Message Batches trade latency for price: batches bill all usage at 50 percent of standard API prices. Batches carry their own rate limits, shared across all models: a requests-per-minute limit on the API endpoints and a ceiling on how many batch requests sit in the processing queue at once. Standard Start, Build, and Scale limits illustrate how endpoint RPM and queue depth scale separately.

Usage tier Batches API RPM Queued batch requests Requests per batch
Start 1,000 200,000 100,000
Build 2,000 300,000 100,000
Scale 4,000 500,000 100,000

These are two budgets: polling consumes API RPM, while every queued item consumes queue capacity. A single batch is capped at 100,000 requests or 256 MB, whichever binds first.

Submit with POST /v1/messages/batches, passing requests as objects of custom_id and params, where params holds the individual Messages request. Each custom_id must be unique within the batch and matches results to requests, because results may come back out of order. Nearly any Messages API request can be batched. The parameters stream, speed, fallbacks, and max_tokens: 0 are unsupported; max_tokens must be at least 1. Results stream as JSONL with a per-item custom_id and one of four result.type values — succeeded, errored, canceled, or expired — and errored or expired items are not billed.

Two clocks govern the pipeline. Results are readable when all messages complete or after 24 hours, whichever comes first, and a batch expires if processing has not finished within 24 hours. Results stay downloadable for 29 days after creation; after that the batch remains visible but its results do not. Cache hits are best-effort because batch requests run asynchronously and concurrently, so do not plan around cached prefixes as you would interactively. Most batches finish within an hour, but processing can take up to 24 hours and slower jobs may expire.

A batch pipeline that survives restarts keeps durable state of its own:

  1. Persist a manifest per job with a stable job ID, its custom_id, an input fingerprint, submission state, and the batch ID once known, so an ambiguous submission gets reconciled rather than blindly resent.
  2. Shard work by encoded byte size and request count, and submit inside both queue and endpoint headroom.
  3. Poll with backoff, then persist results well before the 29-day retention window closes.
  4. Join results by custom_id, never by position.
  5. Reconcile every item, repair invalid inputs, and resubmit only retryable or expired work, after checking whether the first attempt already caused external side effects for tool-enabled jobs.

Make downstream writes idempotent: resubmission and partial success are normal outcomes.

Capacity planning and the binding constraint

Plan against the smallest of three ceilings. Compare peak short-window demand, not minute averages, to RPM, ITPM divided by charged input per request, and OTPM divided by actual output per request, then hold headroom for variance, growth, cache misses, and retries.

The arithmetic below is hypothetical planning, not a runnable example. Assume one model bucket at 1,000 RPM, 2,000,000 ITPM, and 400,000 OTPM, a steady 400 requests per minute offered, and no workspace sublimits, ramping, retries, or burstiness.

Condition Charged input/request Actual output/request RPM load ITPM load OTPM load Tightest
Before growth 2,000 400 40% 40% 40% Three-way tie
After growth 6,000 400 40% 120% 40% ITPM binds
After stable-prefix reuse 3,000 charged + 3,000 cache-read 400 40% 60% 40% ITPM still tightest

At 6,000 charged tokens per request the input bound is 2,000,000 divided by 6,000, about 333 requests per minute, while RPM and OTPM each allow 1,000. If all 400 requests arrive and the system holds that simplified bound, the backlog grows by roughly 67 requests per minute. Halving charged input by serving half the prompt from cache lifts the bound to about 667 requests per minute, but only if those tokens are genuine reads: first-time writes count, and a cold or invalidated cache undoes the gain. Real scheduling must still leave burst and ramp headroom beneath the ceiling.

Batch economics are a different kind of ceiling. If 100,000 of those tasks have no interactive deadline and cost a hypothetical $0.02 each at standard prices, the simplified token bill is $2,000, and 50 percent batch pricing makes it $1,000. That count exactly reaches the 100,000-request ceiling, so encoded size may force multiple batches. The comparison ignores best-effort cache hit rates, failures, retries, and pipeline labor. Test the business deadline and your real rates before assuming the discount outweighs the delay.

Decision criteria

Choose the remedy from the counter that binds, the interval that rejects, and the deadline you must meet.

  1. Reduce request count or burst shape when RPM binds: batch calls, coalesce, and spread retries instead of releasing synchronized fan-out.
  2. Cut charged input tokens when ITPM binds: cache stable prefixes so reads stop counting, and prune what stays uncached.
  3. Reduce generated output when OTPM binds: the counter tracks tokens actually produced, and max_tokens does not itself count toward the limit.
  4. Ramp instead of scaling out when 429s appear below steady-state ceilings and ramp_limit_exceeded is present.
  5. Move to batch when work is offline-tolerant and the 50 percent reduction beats the value of waiting.
  6. Isolate at the tenant layer when one workload consumes shared capacity: workspace limits, scoped keys, and gateway-side accounting.

Collect per-bucket telemetry: RPM, ITPM split into uncached and cache-creation, OTPM, cache-read share, queue age and wait, in-flight work, the reason behind every 429, spend, and per-item batch outcomes. Reserve headroom above the busiest short window you measured, not above the average.

Failure modes and recovery

Three throughput risks are miscounted tokens, assumed reservations, and blanket retries.

Common mistake Counting cache reads against ITPM, or trusting a minute average

Only input_tokens plus cache_creation_input_tokens count toward ITPM, so cache reads do not consume ITPM while cache writes do. Size against reads and you under-provision the moment a cache goes cold. Separately, max_tokens does not count against OTPM. A per-minute average is not burst protection: a 60 RPM allowance can be enforced as 1 request per second.

Common mistake Assuming a workspace cap reserves capacity

Workspace limits are configurable ceilings, while organization-wide limits always apply even if workspace allocations sum to more. Multiple keys in one workspace do not provide per-tenant accounting; use gateway-level accounting or separate workspaces when tenant isolation is required.

Common mistake Running a retry loop against every 429

A tier spend cap returns 429 with enforced_spend_limit_reached and no retry-after, and retries — including SDK-automatic ones — keep failing until access resumes. Classify first: rate and ramp 429s recover with pacing and time, while a cap 429 needs budget or tier remediation, and a configured spend limit arrives as 400 with invalid_request_error outside the Claude Code workspace exception.

Two further traps. Assuming a batch finishes within an hour is wrong: results become available when all messages complete or after 24 hours, unfinished work expires at 24 hours, and downloads stop after 29 days. Assuming output mirrors submission order loses results too, since they may return out of order and must be joined by custom_id. Batches can also overshoot a configured workspace spend limit slightly because processing is concurrent, so keep stricter local budgets.

Exam lens

Exam lenseditorial inference

These are decision patterns for scenario reasoning, not exam questions.

  • Steady RPM, rising uncached prompt length, input-rate 429s: the constraint is ITPM, and smoothing request bursts alone will not fix a sustained input deficit.
  • A workspace cap can contain one tenant when the application maps that tenant to a workspace, but the organization limit still bounds total capacity.
  • Deadline-tolerant offline work favors batch economics at 50 percent of standard prices; a strict synchronous SLA, or items coming back expired, changes the answer.
  • A ramp 429 below steady-state ceilings calls for gradual growth; a monthly spend-cap 429 calls for budget or tier remediation, not retries.
