Key points

  • Branch on stop_reason, not HTTP status: a 200 can report a truncated, paused, or refused turn.
  • A spend-cap 429 (enforced_spend_limit_reached) carries no retry-after, so retries keep failing until access resumes.
  • The SDKs already retry twice by default, so an outer loop can triple load; cap it with a process-wide retry budget.
  • A refusal is a policy stop and the same model usually refuses again: discard partial output, then reset context or fall back.
  • Fail over only after verifying feature parity; Azure-hosted Foundry rejects unsupported features with 400 Bad Request.

Reliability engineering for Claude services matches each recovery action to the exact signal a response carries. A production integration can encounter a failure at three layers: an HTTP status, an event: error frame inside a successful stream, or a 200 OK whose stop_reason reports a truncated, paused, or refused turn. Each signal requires a different response: a monthly spend cap keeps failing under retries, the same model usually refuses a declined request again, and an unverified failover can produce 400 Bad Request responses on Azure-hosted Microsoft Foundry. A resilience pattern maps each signal to one action: fail fast, retry within a budget, resume the turn, degrade the workload, or move to another pool.

Read the signal before you react

Transport failures arrive as an HTTP status and a JSON body shaped {"type": "error", "error": {"type": "...", "message": "..."}, "request_id": "req_..."}, with an optional error.details object on errors such as spend-cap and ramp-limit 429s. Use status, error.type, and details to investigate the cause and decide whether retrying can help.

Log correlation identifiers on every call: every response carries a request-id header, error payloads echo it in request_id, and the Python and TypeScript SDKs expose _request_id on top-level response objects. Claude Platform on AWS returns two headers — x-amzn-requestid (primary, indexed in CloudTrail) and request-id (for Anthropic support).

Client and account errors generally need a change before a retry can succeed:

  • 400 invalid_request_error covers malformed requests, unsupported model parameters, and a user-configured organization or workspace spend limit (Claude Code workspaces may return 429 instead).
  • 401 authentication_error covers a malformed, revoked, or expired API key, an AWS SigV4 failure on Claude Platform on AWS, and browser CORS rejection under custom retention or compliance settings such as Zero Data Retention (ZDR) or the Compliance API, which you fix by calling from your own back end.
  • 402 billing_error, 403 permission_error, and 404 not_found_error signal payment failures, missing key or workspace permissions, or unknown paths and resource IDs.
  • 413 request_too_large enforces payload caps: 128 MB on first-party Messages and Token Counting endpoints (rejected by Cloudflare before reaching API servers), 20 MB on Amazon Bedrock, 30 MB on Google-managed Vertex AI, and 32 MB on Claude Platform on AWS, Anthropic-managed Google Cloud, and Microsoft Foundry.

Conflict and transient errors behave differently. 409 conflict_error sits in between: resolve the concurrent modification or duplicate value before retrying. 429 rate_limit_error spans RPM, ITPM, OTPM, ramp limits (ramp_limit_exceeded), and monthly tier spend caps (enforced_spend_limit_reached). 500 api_error and 504 timeout_error are server-side (timeout_error can also arrive with 500 if the server time limit is reached before the response starts), and 529 overloaded_error signals high traffic across all users.

Retry and backoff design

Retry and backoff design caps how many times a client re-sends a transient failure and spaces attempts out so stressed backends can recover. The official Python and TypeScript SDKs default to max_retries=2 (maxRetries: 2 in TypeScript) — three attempts per call — retrying connection errors, 408, 409, 429, and >=500 with exponential backoff while honoring retry-after. Timeouts retry twice by default as well.

Timeout behavior differs between Python and TypeScript. Both default to 10 minutes; Python raises ValueError if a non-streaming request is projected to exceed roughly 10 minutes unless you pass stream=True or override timeout. TypeScript scales non-streaming timeouts dynamically by max_tokens up to 60 minutes unless overridden, and throws APIConnectionTimeoutError on timeout. Stream long-running requests to avoid idle connection drops.

Because an SDK already makes three attempts by default, wrapping it in an outer three-attempt loop can multiply load to nine requests per original call during a 529 incident. Prefer setting max_retries=0 when an orchestrator owns retries, or reserve the outer loop strictly for cross-platform and cross-model hops. Pair a per-request cap with a process-wide retry budget — such as 10 percent of normal requests — to hold worst-case overload amplification near 1.1x instead of 3x. Add randomized delay (jitter) to prevent synchronized retry waves, and pass deterministic idempotency keys to external mutation APIs so replays do not duplicate side effects.

Rate-limit accounting determines how much headroom your retry budget has:

  • Limits use a continuously replenished token bucket rather than fixed-interval resets, so short bursts can trigger 429s below your per-minute average.
  • Default ITPM limits count uncached input tokens (input_tokens plus cache_creation_input_tokens), excluding cache_read_input_tokens.
  • OTPM meters actual generated tokens in real time, so a higher max_tokens value consumes no extra OTPM quota.
  • Changing inference_geo between "us" and "global" adds no rate-limit headroom because both draw from one pool.
  • Response headers report retry-after in seconds (omitted on tier spend-cap 429s) and anthropic-ratelimit-* limits, remaining counts, and RFC 3339 reset timestamps, with anthropic-ratelimit-tokens-* showing the most restrictive active limit.

Tool loops also need an explicit bound: returning is_error: true in a tool_result lets Claude call the tool again with a new tool_use block, so cap how many retries the harness permits. Tool side effects may persist across retries; prefer storing tool results keyed by tool_use_id and passing deterministic idempotency keys to external mutation endpoints.

Consider a service sending 1,000 requests per minute to claude-opus-5-5 against Start-tier limits of 4,000 RPM, 2,000,000 ITPM, and 400,000 OTPM, where each call sends a 15,000-token system-and-tool prefix plus 1,000 new input tokens. Without prompt caching, all 16,000,000 input tokens per minute count against ITPM — eight times the limit, triggering 429s. Once every request reads the 15,000-token prefix from cache, the remaining 1,000,000 ITPM leaves 50 percent headroom; initial cache writes and misses still count. Under a severe 529 brownout, three attempts per failed call can push total load toward 3x nominal, whereas a strictly enforced budget of 100 retries per 1,000 original requests limits total traffic to 1,100 RPM for that window.

The following Python example disables SDK retries and classifies a 429. It leaves retry scheduling, shared budgets, and failover to the caller; it does not automatically replay requests or tool side effects.

import anthropic
from anthropic import Anthropic

client = Anthropic(max_retries=0)


def send_once(messages):
    try:
        return client.messages.create(
            model="claude-opus-5-5",
            max_tokens=1024,
            messages=messages,
        )
    except anthropic.RateLimitError as exc:
        body = exc.body if isinstance(exc.body, dict) else {}
        error = body.get("error") or {}
        details = error.get("details") or {}
        if details.get("error_code") == "enforced_spend_limit_reached":
            raise RuntimeError("Tier spend cap reached; alert billing") from exc
        # Hand the status and response headers to the caller's retry scheduler.
        raise

Circuit breakers and graceful degradation

A circuit breaker is a per-endpoint state machine that stops sending traffic to a failing dependency. Prefer one three-state breaker per endpoint (closed, open on sustained 5xx, 529, or timeouts, then half-open with a single probe) paired with token-bucket retry throttling, so an unhealthy endpoint fails fast to an independent capacity pool such as Claude Platform on AWS. Trip breakers on availability signals only: never open a breaker on 400, 401, 403, 413, or stop_reason: "refusal", which reflect your payload, credentials, or safety policy.

Graceful degradation preserves a reduced service when capacity is constrained. Choose options that fit the workload, for example:

  1. Defer batchable work to the Message Batches API, which uses separate rate limits and is exempt from ramp limits.
  2. Reduce generation effort where supported, or shrink input by compacting and pruning conversation history.
  3. Fail over to an independent pool only after verifying feature parity — replace server-side fallbacks with client-side fallback logic, or drop server tools, before routing to Bedrock, Google-managed Vertex AI, or Foundry.
  4. Degrade to a model with separate rate-limit headroom on your tier, and flag degraded output for downstream callers if quality tolerances are strict.

Telling rate limits, refusals, and context-window stops apart

Rate limits, safety refusals, and context-window stops represent quota exhaustion, policy intervention, and capacity bounds, and each requires a different recovery path. A 429 with error.details.error_code set to enforced_spend_limit_reached is a hard monthly tier cap with no retry-after: retries keep failing until access resumes, so abort and alert billing. For a rate or ramp limit (ramp_limit_exceeded), honor retry-after when present, pace traffic, and consider prompt caching. A classifier refusal arrives as HTTP 200 with stop_reason: "refusal", and any partial output streamed before it must be discarded. Context-window stops also arrive as HTTP 200 and require context compaction or pruning, not a new capacity pool.

stop_reason (HTTP 200) What happened Recovery
end_turn Claude completed generation naturally; branch on stop_reason rather than HTTP status. Use the response.
stop_sequence Generation matched one of your stop_sequences. Inspect stop_sequence and handle as complete.
max_tokens Output reached the max_tokens cap and may be truncated. Raise max_tokens, continue, or flag partial output. The setting alone does not consume extra OTPM.
tool_use Claude called a client tool; when Claude calls a client tool and a server tool in the same parallel group, the API returns tool_use before running the server tool. Append assistant content unchanged, then send a user message with tool_result blocks first (and only tool_result blocks, with no trailing text, when a waiting server or MCP tool lacks a result), keeping tools; also return any container ID and the same mcp_servers for a waiting MCP call. Report failures with is_error: true and bound retries.
pause_turn A server-tool loop hit its iteration cap, 10 iterations per request by default. Append paused assistant content unchanged with no trailing user message, keep tools, and echo container.id if present inside a bounded loop.
refusal A safety classifier intervened; stop_details carries type, nullable category and explanation, and optional recommended_model. Discard partial output, then reset context or switch models — the same model usually refuses again.
model_context_window_exceeded Generation filled the context window before max_tokens; automatic on Sonnet 4.5 and newer, while earlier models require model-context-window-exceeded-2025-08-26 (typed in the SDK beta namespace). Compact or prune context, or split the work.

Server-side fallback is the simplest refusal recovery where supported: pass fallbacks: "default" (or up to three fallback models) with the server-side-fallback-2026-07-01 beta header, which is in beta on the first-party Claude API and Google Cloud (Anthropic managed), and unavailable on Claude Haiku 5.5, Amazon Bedrock, Google-managed Vertex AI, and Microsoft Foundry. Server-side fallback handles classifier refusals, not rate limits, overload, or server errors. Elsewhere, consider the SDK's client-side refusal-fallback middleware (BetaRefusalFallbackMiddleware), which retries across your fallback list on any platform and applies fallback credit when available; Haiku 5.5 refusals carry no credit. For reasoning_extraction refusals, no fallback model is recommended, so revise the prompt or use adaptive thinking with display: "summarized" instead of retrying.

Mid-stream failure is the fourth recovery path. Once 200 headers are sent, an API error may arrive as event: error (such as overloaded_error), and SDK HTTP retry logic cannot fire retroactively. Interrupted tool_use and thinking blocks cannot be partially recovered; resume from the most recent text block. On Claude 4.6 and later models, resume with a user message telling the model to continue — assistant prefill is unsupported and returns 400 invalid_request_error.

Cross-platform fallback and feature parity

Cross-platform fallback routes traffic to an independent capacity pool during a sustained outage, while feature parity defines the endpoints, tools, and response headers that the target pool actually supports. Every platform enforces different payload limits, routing models, and feature sets. Claude Platform on AWS is the closest drop-in: its pool is separate from both the first-party Claude API and Amazon Bedrock, so multi-platform workloads can fail over between them with near-complete Messages API parity. Decision criteria

Choose each recovery action from the response signal rather than raw error counts. Inspect fields in order: HTTP status, error.type, error.details.error_code on 429s and available retry-after and anthropic-ratelimit-* headers; inspect stop_reason and any stop_details on successful Messages responses.

  1. Fail fast on 400, 401, 402, 403, 404, 413, and spend-cap 429: retrying cannot fix request shape, credentials, billing, permissions, or payload size.
  2. Retry within budget on 408, rate or ramp 429, 500, 504, 529, and timeouts, honoring retry-after with jitter.
  3. Retry conditionally on 409 after resolving the conflicting resource state.
  4. Handle at the response layer on any 200: raise max_tokens or continue, resume pause_turn, run bounded tools, switch models on refusal, and compact on context overflow.
  5. Fail over only after confirming the target pool supports every feature and payload size in the request.
  6. Degrade the workload — batch, reduce effort, shrink context, or shift to a model with separate rate-limit headroom — when retries and failover are exhausted.

Log per-incident signals: HTTP status and error.type, presence of retry-after, the tightest anthropic-ratelimit-* limit, retry ratio, circuit-breaker state per endpoint, and the stop_reason distribution. Investigate rising refusals for prompt or traffic-mix changes; investigate rising 529 rates for upstream capacity pressure.

Failure modes and recovery

Stacked retries, blind 429 retries, same-model refusal retries, and parity-blind failover are common failure modes.

Common mistake Stacking an outer retry loop onto SDK retries

The SDKs already retry transient failures twice by default, so a naive three-attempt outer loop turns three attempts into nine while the API is most stressed. Set max_retries=0 when your orchestrator owns retries, and enforce a per-client retry budget near 10 percent plus jitter.

Common mistake Retrying a refusal on the same model

A refusal is a policy stop: re-sending a refused request to the same model usually triggers another refusal, so discard partial output and consider an appropriate fallback or reset context. For reasoning_extraction, revise the prompt — no fallback model is recommended.

Common mistake Treating cross-platform failover as a URL swap

Server-side fallbacks, the Files API, server tools, code execution, programmatic tool calling, and Agent Skills are not uniformly available, and Azure-hosted Foundry rejects unsupported features with 400 Bad Request. Gate failover on the features the request uses; Claude Platform on AWS keeps near-complete parity on its own capacity pool.

Two stream and turn-continuation traps also require explicit handling: resuming a Claude 4.6+ stream with assistant prefill returns 400, so capture received text and continue from a user message; and on pause_turn, return the container ID if present to retain its files, and continue without a trailing user message.

Exam lens

Exam lenseditorial inference

  • Branch on stop_reason, not HTTP status: a 200 can be truncated (max_tokens, model_context_window_exceeded), paused (pause_turn), or refused (refusal).
  • Separate a spend-cap 429 (enforced_spend_limit_reached, no retry-after) from a rate or ramp 429 (pace retries, honor retry-after when present, and consider caching).
  • Check parity before failover: Bedrock, Google-managed Vertex AI, and Azure-hosted Foundry lack server-side fallback and several tool and file APIs; Claude Platform on AWS keeps near-complete parity on its own pool.
  • Resume mid-stream failures on Claude 4.6+ with a user message, discard unrecoverable tool_use and thinking blocks, and do not stack outer retries without considering retry budgets and side effects.
