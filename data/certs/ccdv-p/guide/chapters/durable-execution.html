Key points

  • Each store covers different state: resume restores the transcript, not the filesystem or what a tool did externally.
  • Claude Code does not rerun an interrupted tool call, so side effects need a write-ahead step log and a deterministic idempotency key.
  • Checkpointing reverts files, never the conversation, and files changed only by Bash are not tracked.
  • Keep running conversations on their last successful system and tools: a prefix edit can fail the check with a 400.
  • Hosted Managed Agents keeps history server-side, so it is ineligible for ZDR and HIPAA; only self-hosted Managed Agents is eligible for ZDR.

Durable execution is the property that a long-running agent can lose its process and still pick up where it stopped. In Claude's tooling it is split across stores with different boundaries: the Agent SDK writes a session transcript to disk automatically, file checkpoints snapshot tracked files, Claude Managed Agents keeps its session log server-side, and everything outside those stores is yours to persist. Those boundaries surface at the same moment, a crash: resume restores the conversation but not the filesystem, checkpoints do not revert files changed only by Bash, and Claude Code does not rerun a tool call that was still running when its process died. Durability depends on knowing which store covers which state.

What each state store covers

Session state is the transcript the harness accumulates: your prompt, every tool call, every tool result, and every model response. File state is what the agent changed on disk. External state is what a tool did to the outside world. Long-term memory outlives one session. Claude's harness writes session transcripts automatically (and captures file checkpoints automatically in Claude Code, or when enabled in the Agent SDK); you manage external state and configure long-term memory.

State Where it lives Boundary you must plan around
Conversation transcript Local JSONL under the projects directory, or a server-side session log in Managed Agents Restores messages only — file edits are not part of it
Tool-edited files Claude Code file checkpoints, 100 most recent per session Reverts files, never the conversation; files changed only by Bash are not tracked
External side effects Your own step log or transactional database Session transcripts record tool calls and results rather than an external transaction log, and Claude Code does not rerun an interrupted tool call on resume
Long-term memory Memory tool files, Claude Code MEMORY.md, Managed Agents memory stores Retention is separate: MEMORY.md and topic files are excluded from the cleanupPeriodDays transcript sweep

Transcripts land at ~/.claude/projects/<encoded-cwd>/<session-id>.jsonl, or under $CLAUDE_CONFIG_DIR/projects/ when that variable is set. Keep session state and business state in different places. Session state is orchestration scaffolding owned by the harness; ledger entries, ticket statuses, and workflow checkpoints belong in a store you own, with explicit schemas. A transcript is a poor system of record: its entry format is internal to Claude Code and changes between versions, so scripts that parse those .jsonl files directly can break on any release. Use the SDK session helpers or /export instead.

Managed Agents draws the same line structurally. It decouples a stateless harness (the "brain"), the sandbox and tools (the "hands"), and an append-only session log, so nothing in the harness needs to survive a crash: a replacement harness is rebooted with wake(sessionId), reads the event log with getSession(id), and resumes from the last event. That log is also the context object living outside the model's context window, which separates durable storage from lossy in-context summarization. The cost is retention: hosted Managed Agents stores conversation history, sandbox state, and outputs server-side; session transcripts persist until deleted, so it is ineligible for HIPAA BAA coverage and ineligible for Zero Data Retention (ZDR) — only self-hosted Managed Agents is eligible for ZDR.

Session persistence, resume, and fork

Session options decide which transcript a run continues. continue picks the latest session in the working directory, resume targets a specific session_id, and fork starts a new session_id from a copy of an existing transcript while leaving the original unchanged — the option to try a different direction and come back.

Setting Effect
continue_conversation (Python) / continue (TypeScript) Resume the most recent session in the current working directory.
resume Resume a specific session_id.
fork_session (Python) / forkSession (TypeScript) Branch into a new session_id when paired with resume; Python also exports synchronous fork_session() (with directory, up_to_message_id, and title), and TypeScript exports async forkSession().
resume_session_at / resume_drops_turn resume_session_at loads the resumed transcript only up to and including a given message UUID (Python Agent SDK 0.2.137 or later); resume_drops_turn pairs with it to name the discarded user-prompt UUID so the CLI refuses the resume if non-turn entries sit in the dropped range (Python Agent SDK 0.2.137 or later and Claude Code CLI v2.1.223 or later).
persistSession: false (TypeScript) or CLAUDE_CODE_SKIP_PROMPT_HISTORY in Python's env option Keep the session in memory for one call and suppress transcript writes.

A SessionStore is the adapter that makes a session resumable on another machine: implement append and load and the SDK mirrors JSONL transcripts to an object store, key-value store, or database, so a session created on one host resumes on another running from a matching working directory. Concurrent append calls can race on the session summary sidecar, so serialize the read-fold-write with a transaction, a compare-and-swap, or a per-session lock. Ephemeral workers with no shared disk need one of these, or workflow state externalized into your own records; local ~/.claude/projects/ dies with the container.

File checkpointing and rewind

Checkpointing snapshots files, not conversation. Claude Code captures a checkpoint before each turn-starting user prompt and keeps file snapshots for the 100 most recent checkpoints in a session. Enable it in the SDK with enable_file_checkpointing=True and extra_args={"replay-user-messages": None} (Python), or enableFileCheckpointing: true and extraArgs: { "replay-user-messages": null } (TypeScript), so turn-starting checkpoint UUIDs appear in the response stream. await client.rewind_files(checkpoint_id) in Python and await response.rewindFiles(checkpointId) in TypeScript restore tracked files on disk to that state and leave the conversation history intact. After a stream completes, resume with checkpointing enabled and rewind inside the response loop. From the CLI, CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING=true claude -p --resume <session-id> --rewind-files <checkpoint-uuid> does the same for a headless run.

Three limits bound checkpointing:

  • Only files touched by the file editing tools (Write, Edit, and NotebookEdit) are tracked: a file changed only by Bash is never reverted, though Bash edits to an already-tracked file are undone.
  • Subagent edits are not tracked, while edits from a skill with context: fork running in the foreground are.
  • A forked session does not include the original's file checkpoints, so you cannot rewind it to a checkpoint captured before the fork.

Crash recovery for side effects

Transcript and checkpoint durability do not cover the outside world. Use a write-ahead step log: a transactional record written before the side effect and updated after it completes. In Claude Code, a tool still running when the previous process ended does not get rerun on resume, and a timeout cannot distinguish "never ran" from "ran before the connection dropped." Recommended practice for any side-effecting tool:

  1. Derive a deterministic idempotency key: a stable identifier built from the workflow run id, step name, tool name, and a hash of the canonicalized arguments, so a retry reproduces the same value. Never use a fresh uuid4() per attempt.
  2. Check the step log before calling the external API. On SUCCEEDED, return the cached result instead of calling again. On IN_FLIGHT, completion is uncertain: query a reconciliation endpoint by idempotency key, retry only if you have verified that repeating the operation is safe, for example because the provider enforces the same idempotency key, or return an uncertain-completion error payload (such as {"error": "uncertain_completion"}) to Claude.
  3. Atomically claim the step before executing it, and prevent concurrent workers from issuing the same operation. A lease expiring alone does not prove that the previous call stopped.
  4. Persist the external result to the step log before appending the tool_result block to the transcript.
Step status Meaning on recovery Action
SUCCEEDED The side effect completed and its result is durable Replay the cached tool_result; do not call the API again
IN_FLIGHT Crashed mid-call; completion unknown Reconcile by idempotency key; retry only when repetition is verified safe
FAILED_TERMINAL Deterministic failure, recorded with its payload Surface the failure; no retry
UNCERTAIN Timed out with no reconcilable answer Report uncertain_completion to the model and to your caller

The MCP specification defines ToolAnnotations.idempotentHint, default false, meaning repeated calls with the same arguments have no additional effect on the tool's environment. Treat it as an untrusted hint, not a guarantee.

For example, a payment worker records IN_FLIGHT before sending a charge with a provider-supported idempotency key. If the worker crashes after the charge, a replacement first reconciles with the provider. If it finds the receipt, it records SUCCEEDED and returns the receipt. If the provider cannot establish the outcome and does not guarantee safe retries, the worker reports uncertainty for human resolution. A unique step key and an atomic claim prevent concurrent workers from both starting the charge; a provider's idempotency guarantee still matters when a worker loses its lease during a call.

Bound the retries themselves. The official SDKs already retry transient failures — connection errors, rate limits, and 5xx server errors — with exponential backoff, twice by default, honoring retry-after when present, under max_retries (Python) or maxRetries (TypeScript). A mid-stream SSE error after HTTP 200 does not follow the standard error-handling mechanisms. Give your step loop its own max_attempts budget with randomized exponential backoff plus jitter, since unbounded retries amplify load exactly when a dependency is degraded.

Checkpointing is not a rollback for external effects: rewind_files() reverts tracked local files, not HTTP POSTs, emails, or external database writes triggered via Bash. Recommended practice: gate irreversible calls behind approvals, and pair each committed external step with a compensating action such as refund_payment or void_invoice recorded in the same log.

Surviving a model version change

A model change can affect model availability, prompt caching, and the handling of preserved thinking. A model swap alone does not change a thinking block’s prefix. Anthropic gives at least 60 days' notice before retiring a publicly released model on Anthropic-operated platforms, while Amazon Bedrock and Claude Models on Google Cloud (Google managed) set independent schedules; a retired model fails requests, one of the documented reasons Claude Code does not keep a resumed session's saved model. Otherwise claude --resume and claude --continue keep the saved model, except in cases such as when it is excluded by availableModels, overridden by alias environment variables, or running on a provider with deployment IDs.

Prompt caches are per model, so switching models in Claude Code means the next request reads the entire conversation history with no cache hits even though the content is identical. Budget for a cold read.

Preserved thinking lets Claude reuse reasoning blocks from earlier turns when your code sends them back. Models with preserved thinking — as of November 2026, Fable 5.1/5.2, Mythos 5.1/5.2, Opus 5.5, Sonnet 5.5, and Haiku 5.5 — reject thinking: {"type": "enabled"} with a 400 error, so a client moving a conversation onto one of them sends "adaptive" instead. Thinking blocks that the new model cannot use never cause an error: the API drops them for that request, does not bill them, and Claude answers without that reasoning, with compatibility restored if you switch back. What fails is mutating the prefix. Preserved thinking blocks bind to system, tools, and prior messages, so altering anything before a block can trigger a 400 invalid_request_error reporting an invalid signature and a block bound to a different conversation (on the Claude API and some cloud platforms, Fable 5.2, Mythos 5.2, and Mythos 5.1 return 400 when prefix_mismatch_behavior is unset, whereas Fable 5.1, Opus 5.5, Sonnet 5.5, and Haiku 5.5 may either return 400 or pass the mismatched blocks through; Message Batches items with the setting unset can drop failing blocks instead).

To deploy updated prompts or tool schemas without invalidating running conversations, keep sending each one the system and tools of its last successful request — its newest thinking was produced after that version — and append changes as trailing messages. If a prefix mismatch already happened, set thinking.block_binding.prefix_mismatch_behavior to "drop_block" and send anthropic-beta: thinking-binding-controls-2026-08-01 on every later request in that conversation, because the API does not store the setting between requests. In Managed Agents, model, system, and skills are fixed for the session lifetime and only tools and mcp_servers can change after creation, so plan a model migration as a new session, optionally sharing a memory store when supported.

For a migration, first test a copy of the saved conversation with the target model and the original instructions and tool schemas. Send the target model's supported thinking configuration. If a prefix error occurs, diagnose the changed history and choose a targeted recovery. Do not classify errors by matching their full text; the documentation says diagnostic wording can change. Record any dropped reasoning and verify the resumed workflow before allowing further side effects.

Decision criteria

Choose the store by what must survive.

  1. Continue on the same machine. Default persistence can restore the transcript if the disk survives; persist business state and external effects separately. The SDK writes transcripts to disk automatically.
  2. Continue on a different host. Attach a SessionStore and serialize its sidecar writes, or externalize workflow state into your own versioned records.
  3. Disposable experiment. Disable persistence with persistSession: false (TypeScript) or CLAUDE_CODE_SKIP_PROMPT_HISTORY (Python) instead of accumulating transcripts you will never resume.
  4. Undo file edits, keep the conversation. Use checkpointing and rewind_files(); accept the 100-checkpoint window and the Bash/subagent gaps.
  5. Prevent a second external effect. Step log plus deterministic idempotency key, reconciliation for IN_FLIGHT, compensating actions where reversal matters.
  6. Compliance boundary decides hosting. Hosted Managed Agents is ineligible for ZDR and HIPAA; use self-hosted Managed Agents for ZDR, or the Messages API with client-side memory_20250818 on compliant storage for ZDR and HIPAA.
  7. State must be queryable or migratable. Application database with schema_version records, not transcript or Markdown scraping.

Evidence to collect per run: the session_id, the checkpoint id you might rewind to, step-log status and attempts per idempotency key, which system and tools snapshot the last successful request used, and whether the model of record is near retirement.

Failure modes and recovery

Most durability incidents are one store being trusted to cover another.

Common mistake Assuming resume replays a crashed tool call

Claude Code does not rerun an interrupted tool call; blindly rerunning a non-idempotent call can produce duplicate charges or writes. Recover from the step log: replay the cached SUCCEEDED result, reconcile anything still IN_FLIGHT, and only retry when you have verified that repetition is safe; an idempotentHint alone is not proof.

Common mistake Treating rewind_files as a general undo

File rewinding restores files on disk and does not rewind the conversation; files changed only by Bash are not tracked, subagent edits are not tracked, and a fork inherits no checkpoints from its parent. External side effects are not covered at all.

Common mistake Editing system or tools on a resumed preserved-thinking session

Thinking blocks are bound to system, tools, and prior messages, so a prefix edit can fail the check with a 400. Keep each running conversation on its last successful system and tools, and apply "drop_block" only as targeted recovery — setting it globally masks prefix bugs and burns tokens.

Five more traps. Leaving thinking: {"type": "enabled"} in a client after migrating to a preserved-thinking model yields that 400 before the conversation resumes. Parsing .jsonl transcripts directly can break on any release; use list_sessions, get_session_messages, fork_session, or /export. Local transcripts on a container filesystem are lost if that filesystem is discarded on replacement. Managed Agents streams need their own recovery: open a new stream first, then list the full event history to seed seen IDs and deduplicate live events, or the reconnect gap loses events. And a session that completes its work goes idle, not terminated — terminated means an unrecoverable error or an archive, while rescheduling is the platform auto-retrying a transient error.

Exam lens

Exam lenseditorial inference

  • Separate transcript, file, and external durability: resume restores the transcript only, rewind_files() reverts tracked tool-edited files only, and external side effects need a step log with idempotency keys.
  • Surviving a mid-session model change: keep running sessions on their last successful system and tools, switch thinking.type from "enabled" to "adaptive", apply "drop_block" only for targeted 400 recovery, and expect a cold prompt cache.
  • Respect hosting boundaries: hosted Managed Agents and its memory stores are ineligible for ZDR and HIPAA; use self-hosted Managed Agents for ZDR, or the Messages API with client-side memory_20250818 on compliant storage for ZDR and HIPAA.
  • For multi-host or ephemeral workers, choose a SessionStore with serialized sidecar writes, shared durable storage, or versioned application state.
