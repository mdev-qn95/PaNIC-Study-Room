This glossary defines service health, Claude API, evaluation, and capacity terms. Its formulas use illustrative numbers; check current documentation for prices, cache limits, and SDK defaults.

Service health and telemetry

An SLI (service-level indicator) is a measured signal of customer-relevant service behavior. SRE guidance recommends writing it as a ratio of two counts: the number of good events divided by the total number of events, for example successful HTTP requests over total HTTP requests. A SLO (service-level objective) adds two pieces to that indicator: a performance goal and a period over which the goal is evaluated against the indicator. Two common SLIs are availability, the proportion of successful requests, and latency, the proportion of requests faster than a defined threshold.

An SLA (service-level agreement) is a contract with the customer or provider that carries stated remedies or consequences; treat it as legal wording sitting on top of your SLOs, not as the engineering target itself. Decide what counts as a good event before you calculate anything: for Claude-backed work you must state how refusals, failed tool sequences, cancellations, and invalid requests enter the denominator, because an HTTP-successful request can still be a refused or incomplete answer.

Messages API and agent execution

The Messages API is stateless: you always send the full conversational history with the request, so no prior turns are held as server-side conversation state for you. Your application therefore owns the loop: it sends history, reads the response, runs tools, and decides whether to call again. Two response fields drive that decision. stop_reason says why generation ended, and the usage block reports token counts used in cost calculations.

Every successful Messages API response includes a stop_reason field that tells you why Claude stopped generating; check it to decide whether to use the response as-is, continue the conversation, retry, or fall back to another model. Documented values include end_turn, max_tokens, stop_sequence, tool_use, pause_turn, refusal, and model_context_window_exceeded. In a stream, stop_reason is initially null; inspect the completed response.

Stop reasons and what to do with them

  • end_turn — Claude completed its response naturally; use the response.
  • max_tokens — Output reached its token limit; treat it as potentially truncated, then continue or raise the budget.
  • tool_use — Claude handed control to a tool call; execute the tool, return the result, then expect the model's next turn.
  • pause_turn — A server-tool loop reached its iteration limit. To continue, append the unchanged assistant content, keep the same tools, and do not append a user message; reuse the container ID if present.
  • refusal — Claude declined to respond; inspect stop_details and apply your safety-handling policy.
  • stop_sequence — A configured stop string ended generation; inspect stop_sequence to see which fired.
  • model_context_window_exceeded — The response filled the model's context window; treat the output as truncated.

Tokens, caching, price, and latency

The usage fields are the least intuitive part of Claude cost accounting. When caching is used, input_tokens represents tokens after the last cache breakpoint, not all the input tokens sent. Total input is cache_read_input_tokens + cache_creation_input_tokens + input_tokens. Read that sum, not input_tokens, whenever you compute a cache percentage or a per-request input volume.

Prompt caching reduces cost and latency by reusing previously processed portions of your prompt across API calls. Writes cost more than plain input and reads cost less: a five-minute cache write is billed at 1.25x base input price, cache reads at 0.1x base input price on most models, and cache reads are charged when a subsequent request retrieves the cached content. Minimum cacheable lengths and the multipliers both vary by model, so check the current prompt-caching and pricing pages before you set a threshold or forecast a bill.

For speed, keep three clocks apart: TTFT (time to first token) measures submission to first token; generation duration measures first token to last token; and end-to-end latency measures task acceptance to your own completion event. Anthropic treats output tokens per second and time to first token as separate speed measures, so report both rather than a single "latency" number.

Reliability, evaluation, statistics, and queueing

A retry repeats a failed operation. Cap attempts. Google SRE recommends exponential backoff with jitter for remote-call retries to dampen error amplification. On Claude, the official SDK already retries transient failures such as connection errors, rate limits, and 5xx server errors with exponential backoff, twice by default, honoring the retry-after header when present. Instrument SDK retries and application retries separately, or you will read one as the other.

Pass@k is the probability that at least one of k generated samples passes the verifier; the original coding formulation checks whether any sample passes the unit tests. Pass^k is the probability that all k trials succeed, and it cannot increase as k grows because demanding consistency across more trials is a harder bar. Choose between them by the outcome you actually care about: selection among candidates versus repeated-run reliability.

Precision is true positives over true positives plus false positives; recall is true positives over true positives plus false negatives. F1 is their harmonic mean, where precision and recall contribute equally, which also means F1 does not represent asymmetric error costs. Cohen's kappa expresses agreement between two annotators as κ = (Po − Pe) / (1 − Pe), where Po is the observed agreement ratio and Pe is the agreement expected when both annotators assign labels randomly. Little's law states that, under steady-state conditions, the mean number of items in a queueing system equals the mean arrival rate multiplied by the mean time an item spends in the system.

Retries and overload

Term Definition

Operational formulas

Each formula names its units and its denominator. Numbers are illustrative arithmetic, not measured service data; prices and multipliers come from the 2026-11-19 documentation and change per model.

  • Request success SLI = good requests ÷ eligible total requests. 9,980 ÷ 10,000 = 99.8%.
  • SLO compliance: measured SLI ≥ target over the declared window. 99.8% measured against a 99.9% 30-day objective is below target for that window.
  • Error budget = 1 − SLO for a ratio SLO. 1 − 0.999 = 0.1%, and over 10,000 equally weighted eligible requests that is 10 bad events.
  • Burn rate = observed bad-event ratio ÷ allowed bad-event ratio. 1% bad ÷ 0.1% allowed = 10x burn.
  • Percentiles: sort the durations and take the stated quantile. Sorted 100, 120, 150, 180, 220 ms gives p50 = 150 ms. Interpolation has no universally accepted method, and five points are too few for a stable tail estimate.
  • TTFT = timestamp(first generated token) − timestamp(prompt submitted). A prompt sent at 12:00:00.000 whose first generated token is observed at 12:00:00.420 gives 420 ms.
  • Output tokens per second = tokens generated during a stated interval ÷ interval duration. If 240 tokens are generated after the first token in 8 seconds, throughput for that interval is 30 tokens/s. Report TTFT alongside it.
  • Cache read share = cache_read_input_tokens ÷ (cache_read_input_tokens + cache_creation_input_tokens + input_tokens). 8,000 read + 2,000 write + 1,000 uncached gives 8,000 ÷ 11,000 = 72.7% read share, which is not a hit rate.
  • Request cache hit rate = requests with cache_read_input_tokens greater than zero ÷ cache-eligible requests. 720 read-hit requests ÷ 900 eligible repeats = 80%. Here, exclude first writes and requests that have no reusable prefix.
  • Effective input cost = [(uncached × base rate) + (write tokens × base rate × write multiplier) + (read tokens × base rate × read multiplier)] ÷ 1,000,000. At an illustrative $3/MTok, 1,000 uncached tokens, 2,000 five-minute write tokens at 1.25x, and 8,000 read tokens at 0.1x give (3,000 + 7,500 + 2,400) ÷ 1,000,000 = $0.0129. Substitute your model's actual rates and multipliers.
  • Cost per successful task = total cost for all attempts ÷ successful tasks. $120 ÷ 800 successful tasks = $0.15 per success, with failed attempts and retries left in the numerator.
  • Retry amplification = provider attempts ÷ original logical operations. 1,400 ÷ 1,000 = 1.4x, that is 40% extra attempts; separate SDK retries from application retries before you diagnose it.
  • Pass@k, with a fixed independent per-attempt success probability p, = 1 − (1 − p)^k. p = 0.8, k = 3 gives 1 − 0.2³ = 99.2% chance that at least one attempt succeeds. Benchmark estimators may differ from this plug-in formula.
  • Pass^k = p^k for independent runs; from n trials with c passes on one task, estimate C(c,k) ÷ C(n,k), zero when the pass count is below k, then average that ratio across tasks. p = 0.8, k = 3 gives 0.8³ = 51.2% all-three success.
  • Precision, recall, F1: P = TP ÷ (TP+FP), R = TP ÷ (TP+FN), F1 = 2PR ÷ (P+R). TP = 8, FP = 2, FN = 4 gives P = 0.80, R = 0.667, F1 = 0.727.
  • Recall@k = relevant items in the top k ÷ all known relevant items for the query. 3 of 5 relevant passages inside the first 10 results gives Recall@10 = 0.60. Choose the unit that enters the context: document, chunk, or evidence span.
  • Cohen's κ = (Po − Pe) ÷ (1 − Pe). Po = 0.90 and Pe = 0.60 give 0.30 ÷ 0.40 = 0.75. Report prevalence and raw agreement alongside it.
  • Power and MDE: power = P(reject H0 given a specified alternative) = 1 − β; MDE is the smallest effect δ for which the planned power(δ; n, variance, α) reaches the target. At α = 0.05 and 80% power, a design calculator might report +5 percentage points as the MDE for its own sample size and baseline variance; that threshold is design-dependent, not universal.
  • Little's law: L = λW under steady state. 40 accepted tasks/s with 2 s average in-system time implies 80 tasks in the system on average. Use steady-state averages, one system boundary, and matching time units.

API facts to re-check before you rely on them

Final Messages API responses expose usage.input_tokens and usage.output_tokens; under caching, total input also adds cache_creation_input_tokens and cache_read_input_tokens, so never use input_tokens alone as total prompt input. Cache fields appear in response usage, or in message_start when streaming; token counts in streaming message_delta events are cumulative.

Version check · Version-sensitive, verified 2026-11-19

Prompt-cache minimum lengths vary by model — shorter prompts cannot be cached even when marked with cache_control — and cache read and write multipliers differ by model and may change, so consult the current prompt-caching and pricing pages before setting thresholds or forecasting spend. The documented SDK retry default of two retries with exponential backoff is likewise an SDK-version-dependent behavior.

Standardize units, windows, and the aggregation method for latency histograms across services: OpenTelemetry histograms exist for statistics such as summaries and percentiles, metrics are measurements captured at runtime, and percentile interpolation has no universally accepted method.

Measurement practice

  • Define task completion before you define the SLI. HTTP success can still be a refusal, an incomplete answer, a failed tool sequence, or a wrong extraction; keep infrastructure success and task success as separate indicators.
  • Track TTFT and end-to-end tail latency separately. Streaming can make output visible sooner while tools or generation still miss your completion objective.
  • Use cache read share for cost composition and the request-level hit rate for cache behavior, and measure only eligible repeats.
  • Specify the experiment metric, baseline, randomization unit, alpha, power, and minimum useful effect in advance. Account for correlation between user turns when estimating sample size.
  • Match the estimator to the question: pass@k when you can select among candidates, pass^k for repeated-run consistency. For capacity, pair arrival rate, residence time, and concurrency; persistent queue growth means arrivals exceed completions.

Where usage connects to outcomes

Record timestamps and token usage on every model call, and count only validated terminal outcomes as successes. Attribute usage from retries and tool loops to the terminal outcome when calculating cost per success.

Worked example: one day of an extraction service

An extraction service has a 99.9% 30-day SLO and receives 10,000 requests/day. On one day it logs 100 task failures and 1,200 provider attempts for 1,000 logical operations. Usage for that day shows 50,000 cache-read tokens, 10,000 cache-write tokens, and 5,000 uncached tokens. Assume $3/MTok with five-minute write and read multipliers of 1.25x and 0.1x. The arithmetic is hand-runnable.

  1. Daily task success ratio = 9,900 ÷ 10,000 = 99%. One day's measurement does not determine whether a rolling 30-day SLO is met; calculate over the actual objective window.
  2. Objective error ratio = 1 − 0.999 = 0.1%, so today's 1% failure ratio is 10x burn relative to the allowed rate.
  3. Retry amplification = 1,200 ÷ 1,000 = 1.2x. Attribute the extra attempts to SDK retry, application retry, or duplicate submissions before you mitigate.
  4. Cache read share = 50,000 ÷ (50,000 + 10,000 + 5,000) = 76.9%.
  5. Effective input charge = [(5,000 × 3) + (10,000 × 3 × 1.25) + (50,000 × 3 × 0.1)] ÷ 1,000,000 = (15,000 + 37,500 + 15,000) ÷ 1,000,000 = $0.0675 at these illustrative prices. Recalculate against the actual model price and applicable multipliers.

Common mistakes

  • Calling input_tokens divided by total input the cache hit rate. input_tokens excludes both cache reads and cache writes, so compute the complete total first.
  • Summing streaming usage snapshots when the message_delta token counts are already cumulative.
  • Comparing p99 values produced by different interpolation or aggregation methods as if the difference necessarily showed a regression.
  • Dividing output tokens by total request duration to claim generation throughput; that denominator may include TTFT plus queue and tool delay.
  • Reporting pass@k as a guarantee that every repeated production run succeeds; pass^k is the all-success event.
  • Reporting raw rater agreement without prevalence context or chance-adjusted kappa, or treating qualitative kappa cutoffs as universal.
  • Treating the MDE as the observed effect, or reading low power as evidence that no effect exists.
  • Applying Little's law to unstable queues, or mixing a per-second arrival rate with a millisecond residence time without unit conversion.
  • Routing refusals, context overflow, and transient transport errors through one generic retry path; stop reasons and API errors need distinct handling.

Exam lens

Exam lenseditorial inference

When a scenario defines an SLI, distinguish response success from task success before choosing the numerator. When it shows usage fields, do not read input_tokens or a token read share as total input or as a request hit rate. When it reports speed, separate TTFT, completion latency, and tail behavior. When it reports an agent benchmark, choose pass@k versus pass^k for the outcome actually measured, and check whether the study had the power to detect the difference it claims.

A

Total input is 500 + 1,000 + 8,500 = 10,000 tokens and the read share is 8,500 ÷ 10,000 = 85%.

A

Pass@2 = 1 − 0.1² = 99%: at least one of two attempts succeeds. Pass^2 = 0.9² = 81%: both attempts succeed.
