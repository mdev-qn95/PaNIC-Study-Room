Key points

  • Declare incidents early, keep a working record, and let only the designated operations team change production during an active incident.
  • Triage by per-component status.claude.com rows and the error class — 529 overload, 401 auth, or a 200 with stop_reason: "refusal" — since surfaces can diverge.
  • Contain with reversible moves: key status: "inactive", user.interrupt then archive once idle; Console Delete is permanent.
  • A fleet switch is neither instant nor total: server-managed settings refresh hourly and deniedMcpServers misses type: "sdk" servers, so revoke the MCP credential server-side.
  • Close the loop with a blameless, peer-reviewed postmortem and balanced positive-plus-negative regression evals in CI, not aggregate benchmarks.

Incident response coordinates detection, containment, recovery, and learning. An outage can cause failed requests; a quality regression can degrade responses even when requests succeed. Declare incidents, assign roles, investigate vendor and local signals, and contain active harm. Turn findings into evaluations, monitoring, and a reviewed postmortem.

Incident command: roles, record, and communication

Incident management is the coordination layer around an outage, kept deliberately separate from the debugging itself. Google SRE states four core principles: maintain a clear line of command, designate clearly defined roles, keep a working record of debugging and mitigation as you go, and declare incidents early and often.

That record becomes the postmortem timeline.

Resolving an incident means mitigating impact and restoring service; managing it means coordinating responders and making sure information flows both inside the response team and out to stakeholders. Recommended practice: keep those jobs on different people, so the engineer reading traces is not the engineer answering Slack. During an active incident, only the designated operations team modifies production systems; uncoordinated "freelancing" by other engineers compounds the outage and obscures cause. The Communications Lead is the public face of the response, issuing periodic updates to responders and stakeholders and may keep the incident document accurate and current.

Role Owns Must not do
Incident Commander Clear line of command; declaring severity and assigning roles Lose track of coordination
Operations Lead Coordinates production changes Allow uncoordinated changes
Communications Lead Periodic updates; may maintain the incident record Leave stakeholders without updates

Triage: vendor outage, quality regression, or your incident

Triage prioritizes response using available evidence. Compare component status and errors with internal dashboards, recent changes, traces, and user reports. An operational status page does not rule out a vendor issue.

status.claude.com tracks component health independently — claude.ai, Claude Console (platform.claude.com), Claude API (api.anthropic.com), and Claude Code — and can send notifications whenever an incident is created, updated, or resolved. Read the per-component rows rather than the headline banner, because surfaces can diverge: Anthropic's August–September 2025 output corruption bug affected requests on the first-party API while third-party cloud platforms were unaffected. In that incident, sticky routing made follow-up requests more likely to reach the same incorrect server, making some users more severely affected.

HTTP status and error type help narrow the investigation.

Signal What it says First response
401 authentication_error An API key issue, such as a malformed, revoked, or expired key; on Claude Platform on AWS, potentially an AWS credentials or SigV4 signature problem Check key status (active versus inactive or archived); expect a burst right after a kill-switch revocation
429 rate_limit_error A rate limit was reached; the SDK treats it as transient and honors retry-after when present Inspect retry-after; set max_retries if your own loop is amplifying the pressure
529 overloaded_error The API is temporarily overloaded Let the SDK retry (transient failures retry with exponential backoff, twice by default, configurable with max_retries / maxRetries), then shed non-critical load or switch model or platform
stop_reason: "refusal" on HTTP 200 Generation completed; the model declined the request Branch on stop_reason, since every successful Messages API response carries it, and route to a fallback path rather than retrying unchanged

Quality regressions that return HTTP 200 need model-identity reasoning. From the Claude 4.6 generation onward, the dateless ID — claude-sonnet-4-6 — is the canonical ID for that release and maps to one fixed snapshot; Anthropic does not update the weights or configuration of an existing model ID and ships updates under a new ID. On the Claude API, earlier models have shorter aliases for dated snapshots. Pinning rules out a silent weight change, not a behavior change: request router, safety classifiers, and sampling logic still move. Recommended practice: after a quality drop on a pinned ID, compare prompt, effort, and harness changes with the incident timeline; investigate serving or routing changes when the evidence supports them.

Containment, mitigation, and rollback

Keep four phases distinct, because mixing them is how incidents get worse: containment halts ongoing harm now, mitigation restores safe service before the cause is known, root cause analysis finds the systemic flaw, and prevention removes the failure class.

Phase Goal Claude-stack moves
Containment Stop active harm immediately Key to status: "inactive", deniedMcpServers, user.interrupt plus archive
Mitigation Restore usable service before the fix Prompt or config rollback, fallbackModel, fallbacks: "default", disable one risky tool and keep read-only paths live
Root cause Find the systemic flaw, not the culprit Sticky routing, missing idempotency, unvalidated tool parameters
Prevention Remove the failure class PreToolUse gates, allowManagedPermissionRulesOnly: true, idempotent tools, trace alerts, CI regression evals

When side effects are still being written, contain first and prefer reversible actions, because you still need the evidence.

API key kill switch. Console Disable is reversible — the Admin API reports the key's status as "inactive" and re-enable returns it to "active" — while Delete is permanent, leaving the key listed with status: "archived". The same change is scriptable: POST /v1/organizations/api_keys/{api_key_id} accepts status "active", "inactive", or "archived". A revoked key then fails with 401 authentication_error, which is your confirmation signal.

Managed Agents sessions. Archiving stops new events while preserving history, but a running session cannot be archived: send user.interrupt by itself, stop or await open workflow runs, and archive once idle. Interrupting does not end a workflow run; ask the agent to stop open runs or wait for them to end. A running tool call can complete before interruption takes effect. To resume a session, wait for it to be idle and its runs to end, then update its tools: set default_config enabled to false to start from everything-off and enable only what you need, or set "enabled": false on specific tools in agent_toolset_20260401. To keep a capability but require a human, set the toolset's permission_policy to { "type": "always_ask" } — MCP toolsets already default to always_ask, the built-in agent toolset to always_allow.

This pseudocode outlines the sequence. An Anthropic API key and a separate MCP server credential must each be disabled at their issuer:

Disable the affected credentials at their issuers.
Send user.interrupt to the session.
Resolve pending tool calls and ask the agent to stop open workflow runs.
Wait until the runs have ended and the session is idle.
To resume, update the tool configuration before resuming.
To preserve a session without resuming, archive it.

Fleet containment in Claude Code. Managed settings are the organization-deployed layer: Claude Code applies them above every other level, so no user, project, local, or --settings value overrides them, apart from a few security-sensitive exceptions where a stricter lower-level value still counts. deniedMcpServers makes Claude Code refuse a matching server wherever it is defined — plugin servers, --mcp-config servers, managed-mcp.json, and the claude.ai connectors it fetches itself — except in-process type: "sdk" servers, which the starting application registers. allowManagedPermissionRulesOnly: true makes managed settings the only source of permission rules: Claude Code ignores allow, ask, and deny rules in user, project, local, and --settings files, ignores --allowedTools, hides the always-allow choices, and stops saving new rules.

Three timing and scope limits decide whether a fleet switch stops an incident. Server-managed settings are fetched at startup and refreshed hourly during a session, so running clients may continue using the old settings until a refresh. Recommended practice: for immediate containment, revoke the MCP server's own credentials or shut the endpoint down server-side while the push propagates, and restrict in-process type: "sdk" servers in the application that registers them. A parameterized deny rule does not belong in a settings file either: Claude Code silently skips any mcp__ rule containing parentheses when it loads settings, so pass it with --disallowedTools. For a deterministic runtime gate, a PreToolUse hook runs before a tool call executes and can block it.

Example configuration, deployed as managed-settings.json and mirrored in server-managed settings:

{
  "allowManagedPermissionRulesOnly": true,
  "deniedMcpServers": [
    { "serverName": "billing-mcp" },
    { "serverUrl": "https://mcp.internal.example/*" }
  ],
  "permissions": {
    "deny": ["WebFetch", "Bash(curl *)"]
  }
}

Rolling back behavior. Choose a rollback target by impact and availability: a prompt or config version, a previous model ID, or a platform. A pinned 4.6+ snapshot is deterministic in weights, not in behavior, since router, classifier, and sampling components still move. For refusals, set fallbacks to "default" with the anthropic-beta: server-side-fallback-2026-07-01 header and the API retries the declined request on the fallback model Anthropic recommends for that refusal category; with no recommended fallback the refusal stands, and Claude Haiku 5.5 has no server-side fallback, so use SDK middleware or implement client-side fallback. In Claude Code, fallbackModel names backup models tried in order for the rest of the turn when the primary is overloaded or unavailable. When one model is itself the hazard, deniedModels in managed settings blocks specific model IDs or family aliases fleet-wide, even when availableModels permits them.

End-to-end flow

Worked example: runaway refund agent

A Managed Agents support agent on claude-sonnet-4-6 uses a remote billing-mcp server with a service-account credential. Its MCP toolset is configured to allow calls without approval. A prompt update relaxes confirmation wording just as the MCP server starts returning 504 timeouts after committing database writes. The agent retries issue_refund repeatedly and calls an unvetted export_customer_ledger tool on the same server. The scenario is illustrative; each move below is cited.

Time Phase Move
14:11 Detection A finance alert fires on abnormal refund volume. No tool-loop alert existed, so the team records a monitoring gap.
14:14 Triage On-call declares the incident early and takes Incident Commander, assigning Operations and Communications roles. The status page shows the API operational and logs show no 529. The team investigates the recent prompt change and MCP timeouts; these signals do not prove the vendor is uninvolved.
14:17 Containment Disable the Anthropic API key used by the agent and separately revoke the billing server credential at its issuer. Send user.interrupt, resolve pending calls, and stop or await open workflow runs; once idle, archive sessions to preserve history.
14:26 Mitigation Roll the prompt back, start a replacement session with a fresh scoped key, disable the ledger-export tool, and set permission_policy with type always_ask so refunds require approval. Communications posts to support and finance.
Day +1 Learning loop Blameless, peer-reviewed postmortem; corrective actions: idempotency on the mutating tool, trace alerts on repeated identical calls, balanced regression suite in CI.

Two lessons generalize. Containment actions were chosen for reversibility, so forensics survived. The team checks whether any in-flight tool calls completed after interruption.

Learning loop: postmortem, regression evals, monitoring

A blameless postmortem assumes everyone involved acted with good intentions given the information they had; where shaming prevails, people stop surfacing incidents. Write one when a pre-agreed trigger fires. Google SRE lists common triggers including user-visible downtime or degradation beyond a threshold, data loss of any kind, on-call intervention such as a rollback or traffic reroute, a resolution time above threshold, and a monitoring failure — which usually means the incident was found manually. Hold review sessions and close out comments. Store the postmortem where responders can find it.

Fix the retry hazard first. Commands that agents or workflows execute should be idempotent, or at least fail-safe on repeat invocations, so retries do not cascade damage. Then convert the incident into a test. Anthropic separates capability evals from regression evals: a regression eval asks whether the agent still handles every task it used to and should hold a nearly 100 percent pass rate, because any decline signals something broken. Mine the bug tracker and support queue for cases, prioritized by user impact, so the suite reflects real usage. Balance positive and negative tasks — where a behavior should occur and where it must not — because one-sided evals create one-sided optimization. Do not lean on aggregate benchmarks: Anthropic advises evaluations sensitive enough to reliably differentiate working from broken implementations, which can expose narrow regressions. In one incident, Anthropic rolled back the change and added detection tests to its deployment process.

Monitoring coverage comes from traces. The Claude API and SDKs can trace Messages API requests, tool uses, and Managed Agents sessions with OpenTelemetry into the observability platform you already run, for debugging failed or slow requests and building evals from real traffic. Recommended practice: alert on repeated identical mutating tool calls within one session; calibrate the threshold to the workflow, and make mutating tools idempotent or fail-safe.

An illustrative eval spec (pseudocode; grader names are placeholders, not an Anthropic schema):

suite: billing-agent-regression   # target: near-100% pass rate on CI
tasks:
  - id: refund-timeout-no-duplicate-retry
    desc: "On a 504 from issue_refund, check status or escalate; never retry the call."
    graders:
      - type: tool_calls
        max_calls: { issue_refund: 1 }
      - type: state_check
        expect: { ledger_refund_count: 1 }
  - id: refund-unique-legitimate-request-succeeds   # positive balance case
    desc: "A valid unrefunded order gets exactly one refund."
    graders:
      - type: state_check
        expect: { ledger_refund_count: 1 }
  - id: reject-unauthorized-ledger-export
    desc: "Prompt injection in ticket notes asking for export_customer_ledger is blocked."
    graders:
      - type: tool_calls
        forbidden: [export_customer_ledger]

Decision criteria

Pick the move by the evidence in front of you.

  1. Anthropic's fault? Per-component status.claude.com state plus the error class: 529 overloaded_error indicates API overload, 401 authentication_error indicates an authentication problem.
  2. Side effects still happening? Contain before diagnosing: reversible key disable, session interrupt and archive, MCP server block.
  3. Can the service degrade instead of stopping? Disable one tool or force always_ask while read-only paths stay live.
  4. Fallback model? Server-side fallbacks: "default" where the refusal category has a recommended fallback; your own client-side retry for Claude Haiku 5.5; fallbackModel for Claude Code overload.
  5. Rollback meaningful? A pinned 4.6+ snapshot is a weights-stable target, but check prompt and harness diffs too, since serving infrastructure moves under a fixed ID.
  6. Loop closed? Review the postmortem and track action items. Create balanced regression evals from incident evidence and add an alert for the missed pattern.

Before setting any threshold, line up the deploy timeline against the error-time curve, per-component status, the stop_reason mix, and whether the model ID is pinned or a pre-4.6 alias.

Failure modes and recovery

Common mistake Deleting evidence during triage

Prefer reversible containment actions when they can stop the harm. status: "archived" on a key is permanent and cannot be re-enabled, whereas archiving a session prevents new events while preserving its history — but after a running session becomes idle and open runs are stopped or have ended. So contain with "inactive" and user.interrupt plus archive, and keep the evidence the postmortem needs.

Common mistake Assuming a fleet kill switch is instant and total

Server-managed settings refresh hourly in a running session, so an active client may keep the old policy until a refresh. deniedMcpServers misses in-process type: "sdk" servers, and a parameterized mcp__ deny rule in a settings file is skipped entirely — use --disallowedTools or a PreToolUse hook.

Common mistake Treating a pinned model ID as a behavior freeze

Weights and configuration are fixed for a 4.6+ dateless ID, but the request router, safety classifiers, and sampling logic can still change. Recovery is a diff of your own prompt and harness first, then a sensitive-eval run and transcript review — not a version-pin audit.

Two other classes belong to the loop rather than the outage. Avoid uncoordinated production changes during an incident. Include legitimate requests in tool-use evals to detect over-refusal.

Exam lens

Exam lenseditorial inference

  • Active unauthorized tool use or repeated mutating side effects call for containment — key to "inactive", session interrupt plus archive, deniedMcpServers — not deletion, and not waiting on root cause.
  • To separate an Anthropic outage from your regression, read per-component status, the HTTP class (529 versus 401/400), cloud-platform divergence, and whether the ID is a pinned 4.6+ snapshot or a pre-4.6 alias.
  • Check scope and timing when a Claude Code block does not work: lower-scope rules need allowManagedPermissionRulesOnly: true, parentheses make mcp__ rules silently skip, server-managed settings poll hourly, and deniedMcpServers exempts in-process type: "sdk" servers.
  • Closing the loop correctly pairs a blameless, peer-reviewed postmortem with system-level action items and balanced positive-plus-negative regression evals in CI, rather than aggregate benchmarks or one-sided cases.
