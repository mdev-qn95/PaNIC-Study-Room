  • Verification capacity, not generation capacity, sets how much you can delegate; with loops one engineer runs dozens or hundreds of sessions.
  • Give Claude a deterministic pass/fail check and require command output as evidence instead of a claim that tests pass.
  • Introduce a new AI reviewer in shadow or observe mode, then calibrate precision, per-stage recall, and false positives before gating.
  • The review check run never concludes failure, so gate on parsed Important severity or unresolved threads, and fail on a missing verdict.

Verification operations are the controls that decide whether a code change is accepted, and by what evidence, before and after a human reads it. When agents generate code faster than people can review it, review becomes the limiting stage: code output per Anthropic engineer grew 200% year over year, and code review became the a delivery bottleneck. The decisions this skill tests are narrow: which checks to move before the pull request, how to introduce an AI reviewer in shadow mode, what evidence calibrates it before it may block a merge, and where humans stay in the loop.

How the verification funnel works

A verification funnel orders checks from early feedback through review and release. Each stage can catch defects missed by earlier checks. Model-based review sits in the middle; human approval sits at the top, applied by risk.

The volume behind this design is documented. Anthropic engineers ship 8x as much code per quarter as they did from 2021 to 2025, and Anthropic states that reviews and monitoring must scale alongside it or the pipeline becomes an Amdahl's Law bottleneck. In Claude Code's own repository, roughly 90% of the code is authored by Claude; from June to September 2026 merged pull requests more than doubled while the share that had to be reverted fell by more than 40%. Daily landed changes in Anthropic's monorepo went from about 2,500 in May to more than 30,000 in September, which makes manual line-by-line review infeasible at that rate.

Verification capacity, not generation capacity, sets how much work you can delegate. Anthropic's framing is that without verification loops an engineer can supervise only one or two Claude sessions at a time because they must check everything personally, while with them one engineer can run dozens or hundreds in parallel.

Two practices reduce risk. An AI reviewer runs in shadow or observe mode, where it produces comments and logs instead of verdicts, until its measurements justify gating. Protect review configuration so a proposed change cannot weaken the rules used to evaluate itself.

Pre-PR verification loops

A verification loop is a check that returns pass or fail, which lets Claude close the loop itself: make the change, run the check, read the output, fix what broke, run again. Give Claude deterministic signals — tests, a build exit code, a linter, a fixture diff, or a browser screenshot — and require the command output as evidence rather than accepting a claim that tests pass.

Three enforcement points carry most of the load:

  1. Stop hooks run at turn end. A hook that exits with code 2 blocks the stop and feeds its stderr back to Claude; Claude Code applies an 8-consecutive-continuation cap, raised by setting CLAUDE_CODE_STOP_HOOK_BLOCK_CAP. The counter resets when Claude calls a tool. The cap can override a block, so use CI for an independent merge requirement.
  2. /goal wraps a session-scoped prompt-based Stop hook: after each turn, Claude Code sends the condition and the conversation so far to a configured small fast model, which returns Met, Not yet met, or Impossible.
  3. /verify builds the project's app, runs it, and observes the result rather than relying on tests or type checks.

The check itself has to resist gaming. Agents optimize toward the signal in front of them, so Anthropic recommends end-to-end, property-based, and differential tests. In its workflow Claude escalates a check still failing after three repair rounds.

Check What it examines Role
Unit tests A function against a narrow contract Weakest here; pair with broader suites
End-to-end tests A flow through the running app Stronger
Property-based (fast-check, Hypothesis, proptest) Invariants across sampled inputs Stronger
Differential tests Differences between implementations on sampled inputs Stronger
Rubric grader (separate model call) Output against a written quality rubric Up to 10 points better task success than a plain prompting loop in Anthropic's structured-file testing

For security specifically, the security-guidance plugin layers three automatic in-session checks before code reaches a pull request: a deterministic per-edit pattern match with no model involved, an end-of-turn background diff review, and a fresh-context agentic review at commit and push.

Review surfaces: managed, local, and CI

Managed Code Review is Anthropic's hosted reviewer for Team and Enterprise plans on GitHub. It runs on Anthropic infrastructure in four stages: Find, where several agents examine the diff and surrounding code in parallel; Verify, which checks candidate findings against the code and filters false positives; Rank, which deduplicates and orders by severity; and Post, which posts the results. Access is read-only and the service does not execute the reviewed code. Findings are tagged Important, Nit, or Pre-existing.

Admins choose review depth (Quick, Standard, Deep), when reviews run (Once after PR creation, After every push, or Manual, where a review can be requested with @claude review), and monthly spend caps; automatic reviews skip draft pull requests and forks. Average cost runs about $15–$25 per review, billed through usage credits. REVIEW.md customizes what it checks; Code Review reads REVIEW.md from the pull request's base branch or the default branch, never from the pull request's own changes, and honors severity downgrades, exclusions, and nit caps only when branch protection is confirmed.

Merge-gate mechanics

A finished managed review blocks nothing by itself. The Claude Code Review check run concludes neutral, or skipped after pushes that change no files and keep the earlier result; it never concludes failure, so a completed review does not fail a required check, and merge blocking is left to repository rules or your own CI.

Two enforcement routes exist. Requiring GitHub conversation resolution blocks the merge while finding threads stay open. A CI step can instead parse the machine-readable severity comment that Code Review places as the last line of the check run's output.text, gate on Important findings there, and treat a missing severity line as no verdict rather than zero findings — a failed, timed-out, canceled, or superseded run and some completed reviews omit the line. Read output.title first: a title beginning Code review not repeated means earlier Important findings are still open, while a title ending no new changes allows a pass.

A gate should select the current head commit's review and follow the documented title and severity order. Require an explicit successful verdict; handle missing or stale results as no verdict. Conversation resolution alone may not cover findings that GitHub did not accept as inline comments.

Shadow mode, then calibration

Anthropic describes introducing its new AI reviewers in shadow mode: the agent posts comments for human approval until trust is earned, and the team red-teams it by trying to insert malicious changes. Anthropic's commit gate uses three modes — off, observe, and enforce — where observe logs what would have been blocked so false positives can be reviewed before anyone is impacted. A reviewer that starts as a hard blocker on day one converts an unmeasured model into a delivery outage.

Calibration measures reviewer findings against human judgments before a team grants gating authority. Anthropic scores candidate reviewers against an eval set built from past incidents and reverts, with expert-confirmed keys, plus clean merged pull requests as a control for over-flagging, and records recall separately at raw findings, post-verification, and final review. Stage-by-stage recall matters because an end-to-end score cannot tell you whether discovery missed a bug or the false-positive filter dropped a bug it had already found.

Metric Definition What it detects
Precision Fraction of flagged PRs that were truly defective Alert fatigue from over-flagging
Recall, per stage (raw, post-verification, final) Fraction of defective PRs found at each stage Bugs lost to an over-aggressive verification filter
False-positive rate Fraction of clean control PRs wrongly flagged Measures over-flagging
Comment disposition Fixed, rejected as wrong, intentional, or ignored Whether humans act on the findings
Rounds to pass Review-fix cycles until green Convergence failure in the author-reviewer loop

Internally, Code Review raised pull requests receiving substantive comments from 16% to 54%; on PRs over 1,000 lines changed, 84% get findings averaging 7.5 issues, against 31% and 0.5 issues on PRs under 50 lines, and less than 1% of findings are marked incorrect.

Run this evaluator, which is runnable Python 3, on a shadow-mode window to decide whether a reviewer earns gating authority. It scores flagged PRs against incident and revert ground truth plus a clean-PR control set, inspired by Anthropic's calibration design; the acceptance thresholds are examples to set from your own cost of a wrong verdict.

# Runnable Python 3.10+ (standard library only) — Shadow-Mode Reviewer Gate Evaluator
from dataclasses import dataclass

@dataclass(frozen=True)
class ShadowEvalCounts:
    tp: int  # Defective PRs correctly flagged as Important
    fp: int  # Clean control PRs wrongly flagged as Important
    fn: int  # Defective PRs missed (passed as clean)
    tn: int  # Clean control PRs correctly passed

    def metrics(self) -> dict[str, float]:
        if min(self.tp, self.fp, self.fn, self.tn) < 0:
            raise ValueError("counts must be nonnegative")
        if not (self.tp + self.fp and self.tp + self.fn and self.fp + self.tn):
            raise ValueError("precision, recall, and false-positive rate require denominators")
        precision = self.tp / (self.tp + self.fp)
        recall = self.tp / (self.tp + self.fn)
        fpr = self.fp / (self.fp + self.tn)
        f1 = 2 * precision * recall / (precision + recall) if precision + recall else 0.0
        return {
            "precision": round(precision, 4),
            "recall": round(recall, 4),
            "fpr": round(fpr, 4),
            "f1": round(f1, 4),
        }

def ready_for_merge_gate(
    counts: ShadowEvalCounts,
    min_precision: float = 0.80,
    min_recall: float = 0.75,
    max_fpr: float = 0.05,
) -> tuple[bool, dict[str, float]]:
    m = counts.metrics()
    passed = (
        m["precision"] >= min_precision
        and m["recall"] >= min_recall
        and m["fpr"] <= max_fpr
    )
    return passed, m

unfiltered = ShadowEvalCounts(tp=38, fp=42, fn=2, tn=118)
calibrated = ShadowEvalCounts(tp=34, fp=6, fn=6, tn=154)

for name, run in [("unfiltered_baseline", unfiltered), ("calibrated_verified", calibrated)]:
    ok, stats = ready_for_merge_gate(run)
    print(f"{name}: gate_ready={ok} metrics={stats}")

In these hypothetical counts, the baseline fails the example gate and the calibrated run clears it. A flagged defective PR is counted as true positive here; a real evaluation should also check whether the finding identifies the actual defect. Recommended practice is to promote only Important findings, or security findings, into a CI merge gate, and only once precision and false-positive rate are measured, REVIEW.md exclusions and nit caps are tuned, and convergence controls are active.

Convergence when the author is an agent

Convergence means a review loop terminates in a bounded number of rounds. It breaks differently when the author is an agent: a person waves off a nit in seconds, whereas an agent fixes it, which means another commit and another round of review. An agent author and an agent reviewer can keep each other busy indefinitely — one Anthropic CLI pull request looped more than 50 rounds overnight — so Anthropic tracks comment disposition and enforces convergence caps.

The Claude Code team asks the author to reconsider after three rounds, uses diff-only re-review after the first few passes, flags bug classes, and avoids repeated findings. Review instructions can also exclude paths and cap nits.

Convergence measure Before After
Passed after one review and fix round 65% 78%
Needed five or more rounds 8.9% 1.5%
Mean reviews to pass 2.08 1.32

Extra rounds consume CI minutes and push commits that invalidate earlier approvals, so suppressing style noise is a throughput measure, not a style preference.

Human oversight design

The Claude Code team allocates human approvals by the risk tier of the change. An agent's approval never counts as a person's: automated review can clear a low-risk change but cannot fill a slot that calls for a human.

Tier Human approvers Condition
Low 0 Trusted author, automated review and security checks pass
Medium 1 A human reviewer is required even when automated review passes
High 2 Highest-risk code and designated paths

Oversight capacity is a measured quantity: track human approvals per pull request at median and 95th percentile, human comments, and how long a pull request waits on a person, with revert and incident rates as the guardrail — if those rise, you have moved human time rather than saved it.

Provenance makes each change auditable after the fact. By default, Claude Code adds a Co-Authored-By commit trailer naming the model in use, including the subagent model for a subagent commit. Anthropic additionally stamps each commit with how it was verified, including the value "none", so unverified commits can be queried across the repository.

Decision criteria

  • Designing the inner loop. Give Claude a deterministic pass/fail check and require command output as evidence; enforce it at turn end with a Stop hook exiting 2.
  • Behavior, not assertions. Use /verify when tests and type checks would not reveal whether the running app behaves correctly.
  • Agent-authored work. Prefer end-to-end, property-based, and differential checks, and cap autonomous repair attempts at three rounds before escalating to a human.
  • Choosing a review surface. /code-review for a fast, unbiased local pass at a chosen effort level; managed Code Review or claude ultrareview for a verified multi-agent sweep of a PR or large diff.
  • Enabling a new reviewer. Start in shadow or observe mode, then compare precision, per-stage recall, and false-positive rate against incident-derived and clean control sets.
  • Promoting a reviewer to a gate. Gate on parsed Important counts or unresolved threads, never on the check run's own conclusion.
  • Setting human requirements. Route by risk tier, keep CODEOWNERS on high-blast-radius paths, and never let a bot approval satisfy a human slot.
  • Judging the change. Believe revert and incident rates over throughput charts.

Failure modes and recovery

Common mistake Making the review check run required

Adding Claude Code Review as a required GitHub status check approves PRs with open Important bugs, because the run concludes neutral or skipped and never failure. Require conversation resolution before merging, or run CI that reads output.title and the severity payload and fails on normal > 0.

Common mistake Reading a missing severity line as zero findings

Failed, timed-out, canceled, superseded, and some completed runs omit the severity comment. Treat a missing line as no verdict and fail closed; an explicit normal: 0 or the documented no-new-changes title can pass.

Common mistake Loading review config from the pull request head

A pull request that can edit its own REVIEW.md can downgrade its own severity, and one that can inject .claude/ or .mcp.json can inject hooks and MCP servers. Code Review reads REVIEW.md from the base or default branch, never from the pull request's own changes, and honors downgrades and exclusions only under confirmed branch protection. The GitHub Action restores its configuration paths from the base branch and warns against checking out untrusted pull request heads on pull_request_target or workflow_run.

Also common, and cheap to fix:

  • One @claude trigger for two systems. @claude review starts the GitHub Action too when it keeps its default trigger_phrase; set the Action to a different phrase.
  • Automatic security scans on fork PRs. claude-code-security-review is not hardened against prompt injection, so require approval for all external contributors.
  • Counting agent approvals as human approvals. Automated review cannot fill a required human slot.
  • Trusting completion claims. Require the command output, and use checks that are hard to satisfy without fixing the defect.

Exam lens

Exam lenseditorial inference

  • A new AI reviewer appears in a high-velocity pipeline. Choose shadow or observe rollout with calibration against human-labeled incidents and clean control PRs before any merge blocking. Compare disagreements with independent human reviewers, adjudicate them, and remeasure on held-out examples after tuning.
  • PRs bounce through dozens of commits, or humans ignore comments. Diagnose nit inflation and missing convergence controls; fix with secondary verification filtering, REVIEW.md exclusions and nit caps, diff-only re-review, and a three-round cap — not a second stacked reviewer model.
  • A PR merged despite open Important findings, or bypassed a review rule. Check whether config was read from the PR head instead of the protected base branch, and whether the gate relied on a neutral check-run conclusion instead of parsing the severity payload or requiring thread resolution.
  • Generation outpaces human capacity. Push deterministic checks and /verify pre-PR, route low-risk trusted-author changes through automated gates, reserve humans for CODEOWNERS paths, and watch revert and incident rates as the guardrail.
