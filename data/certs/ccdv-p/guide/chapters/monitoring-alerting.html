Key points

  • Refusals, max_tokens, and model_context_window_exceeded ride HTTP 200 with stop_reason, so classify terminations, not status codes alone; Claude Code logs refusals as claude_code.api_refusal.
  • For a 30-day SLO, consider paging on 1h/5m at 14.4x and 6h/30m at 6x, and ticketing on 3d/6h at 1x. Adjust for quiet endpoints.
  • Page spend on OTel metrics or the legacy /cost_report; the Analytics API lags 4-to-24 hours and revises until about 7 days after month end.
  • Cost growth with ITPM 429s on flat traffic warrants checking usage.cache_read_input_tokens: cache reads are excluded from default cache-aware ITPM limits.
  • Spend failures differ: 429 with enforced_spend_limit_reached has no retry-after, while a limit you configured returns 400 invalid_request_error (429 in Claude Code workspaces).

Production monitoring turns live responses into ratios and holds them against targets. A service level indicator (SLI) is a quantitative measure of some aspect of service level, aggregated as a rate, an average, or a percentile; a service level objective (SLO) sets the target value or range for it. The error budget is the permitted fraction of unsuccessful events under an SLO. Burn rate measures how fast the service consumes that budget relative to the SLO window. Monitor response outcomes as well as HTTP status: stop_reason reports why generation ended on a successful response.

How it works: signals, budgets, and burn rate

Keep the SLO set small. Google SRE advises choosing just enough SLOs to cover the system's key attributes rather than over-constraining teams. Anthropic recommends evaluating most use cases against multiple success criteria. Choose criteria such as task success, latency, safety, and cost to suit the service.

The error budget is the SLO's complement: a 99.9% target leaves 0.001. Burn rate divides the observed error ratio by that budget: 1 spends the whole budget inside the compliance window, 14.4 14.4 times faster. One window cannot decide an alert, so Google SRE's multi-window, multi-burn-rate (MWMBR) pattern pairs a long window for precision with a short window that confirms burn is active; one-twelfth of the long window is a guideline, so the alert clears soon after recovery. For a 30-day 99.9% SLO the starting points are 14.4x (2% of budget in 1h, short window 5m) and 6x (5% in 6h, short window 30m) for paging, plus 1x (10% in 3d, short window 6h) for tickets.

As engineering practice, cover four layers, not one availability number.

Layer What the SLI counts Signal it reads
Completion yield Valid responses that reached a usable terminal state stop_reason on every HTTP 200 Messages response, plus the status code itself
Latency First-token time and full-turn time, tracked apart TTFT for streaming and interactive apps; ttft_ms on claude_code.llm_request and interaction.duration_ms on claude_code.interaction spans
Behavior and quality Refusals, tool failures, task success, grounded answers stop_reason: "refusal" with stop_details.category; claude_code.tool_result; pass^k; citation-verification pass rate
Unit economics (cost per unit of work) Spend per successful task and cache efficiency Analytics cost rows; cache-read share in Console rate-limit charts

Low traffic makes error ratios noisy: a single failure in a quiet window can push a computed burn rate past a paging threshold, so Google SRE recommends synthetic traffic, aggregating related services, retries or fallbacks, or wider windows for low-volume services and quiet periods. Keep synthetic and real-user results visible separately: successful probes can mask user failures.

Latency, stop reasons, and quality SLIs

Time to first token (TTFT) measures how long the model takes to generate its first output token after receiving the prompt, and helps measure responsiveness in streaming and interactive applications. Anthropic separates baseline latency — prompt processing and response generation independent of token throughput — from TTFT, and exposes output_config.effort to trade latency against reasoning depth, with "low" on Claude Haiku 5.5 as the example. Keep TTFT separate from full-turn percentiles: a turn can include several model calls and tool executions.

Termination quality sits in the response body. stop_reason is part of every successful Messages API response and says why generation ended — end_turn, max_tokens, stop_sequence, tool_use, pause_turn, refusal, or model_context_window_exceeded — whereas errors mean the request itself failed to process. A classifier refusal on supported Claude Fable and Opus models, Sonnet 5.5, or Haiku 5.5 arrives as a normal response, not an error, with stop_reason: "refusal" and stop_details.category naming the policy area. For streaming, read the final stop_reason from message_delta; it is null in message_start. Claude Code's OpenTelemetry export encodes that split: refusals land on a successful stream, so claude_code.api_error does not fire and claude_code.api_refusal carries refusal frequency instead.

Groundedness and tool health need their own indicators. Make answers auditable by having Claude cite quotes and sources per claim, then verify each claim by finding a supporting quote after generation; the pass rate is your grounded-answer rate. Compute tool failure rate from execution results — claude_code.tool_result carries tool_name, success, duration_ms, and error_type — but excludes rejected tool calls; track decisions separately. Managed Agents exposes per-tool counts and failure rates in the Console Inspector Tools tab. For agent tasks, report pass@k (at least one success in k attempts) and pass^k (all k succeed), since pass^k measures consistency across those trials, which can help assess production reliability.

Alert rules and routing

The alert is arithmetic on the error budget; the window pairing helps distinguish sustained burn from a transient spike. The following runnable Python example uses precomputed error ratios for a 99.9% 30-day completion SLO:

def evaluate_slo_alerts(
    err_rate_5m: float,
    err_rate_30m: float,
    err_rate_1h: float,
    err_rate_6h: float,
    err_rate_3d: float,
    slo: float = 0.999,
) -> str:
    budget = 1.0 - slo
    if (err_rate_1h > 14.4 * budget) and (err_rate_5m > 14.4 * budget):
        return "PAGE_CRITICAL_14.4X"
    if (err_rate_6h > 6.0 * budget) and (err_rate_30m > 6.0 * budget):
        return "PAGE_HIGH_6X"
    if (err_rate_3d > 1.0 * budget) and (err_rate_6h > 1.0 * budget):
        return "TICKET_SLOW_BURN_1X"
    return "OK"

Consider steady traffic and no earlier errors. At 14:00 a deploy causes a 0.018 failure ratio. The five-minute burn reaches 18x; the one-hour ratio exceeds 0.0144 just after 14:48, triggering the critical page. Roll back at 14:55: once the five-minute ratio falls below the threshold, that alert clears even if the one-hour ratio remains high. This example assumes uniform traffic, no measurement delay, and the critical rule considered in isolation; the 6x rule can page earlier.

Route severity by burn tier and send other signals to the team that can act on them; thresholds below are illustrative except the burn-rate pairs.

Anomalous usage and spend limits

Spend limits fail in two ways, and the difference decides what retries can do. Hitting a monthly tier cap — $500 on Start, $1,000 on Build, $200,000 on Scale — returns HTTP 429 rate_limit_error with enforced_spend_limit_reached and no retry-after, until the next UTC month unless a higher limit is granted. Hitting a spend limit you configured for the organization or workspace returns HTTP 400 with invalid_request_error (Claude Code workspaces may return 429), and Console can email alerts on those limits. A ramp limit differs: it caps how fast token usage on a model may grow, so after a sharp increase requests return 429 with error.details.error_code: ramp_limit_exceeded even below the nominal ITPM and OTPM limits. For ramp limits, reduce the rate of increase and follow any retry-after guidance. Include the error code in the alert payload.

Isolation comes from workspaces: a workspace (wrkspc_...) holds its own API keys, monthly spend limits, spend-alert emails, and per-model rate limits, and every authenticated response returns anthropic-workspace-id — the field to group spend alerts on. For Claude Enterprise organizations only, not Console organizations, the Spend Limits API reads each member's resolved effective limit and period-to-date spend and manages per-user overrides and limit-increase requests.

Drift after model updates

Automated evals are useful pre-launch and in CI/CD; production monitoring detects distribution drift and unanticipated real-world failures after launch, alongside transcript review. Compare sampled live outcomes with a baseline by task and traffic cohort. Review failing transcripts and retrieval results; validate any judge against human labels before relying on its score. After a model or prompt rollout, compare the canary with the previous version and roll back if the regression is material. Model identity explains some drift and rules out the rest. From Claude 4.6 onward, a dateless ID such as claude-sonnet-4-6 or claude-sonnet-5 maps to a single fixed snapshot whose weights and configuration Anthropic does not change, whereas pre-4.6 models used dated snapshots like claude-sonnet-4-5-20250929 plus optional aliases like claude-sonnet-4-5. Pinning weights does not freeze behavior: serving infrastructure — request router, safety classifiers, sampling logic — can change. Anthropic describes Active, Legacy, Deprecated, and Retired lifecycle stages and gives customers with active deployments at least 60 days' notice before retirement of publicly released models. Amazon Bedrock and Google-managed Vertex AI maintain separate schedules.

Two incidents look alike but differ. A token-cost jump with ITPM 429s and flat traffic can indicate a cache miss. Check usage.cache_read_input_tokens: cache reads are billed at a discounted rate and excluded from default cache-aware ITPM limits, so misses can increase cost and rate-limit pressure. Opt into diagnostics on both requests: send diagnostics.previous_message_id as null on the first and the previous response ID on the next. Diagnostics can identify the first structural divergence; expiry and minimum cacheable length can also cause misses. A refusal or style shift on a pinned 4.6+ ID can reflect serving infrastructure, prompt, or traffic changes; investigate before assigning a cause.

For a planned migration: validate with a regression suite on pass^k, canary the stop_reason mix and token ratios, pin explicit model IDs rather than aliases, and keep refusal rate and transcript sampling running to detect changes on frozen IDs.

Decision criteria

Pick the signal by the question on call.

  1. Is the service up? Completion yield from status codes plus stop_reason, alerted with MWMBR pairs.
  2. Is it fast enough? Streaming TTFT percentiles, then end-to-end latency separately; tune output_config.effort as targets tighten.
  3. Is it answering well? Refusal rate, tool failure rate, pass^k, and grounded-answer rate, from response fields, tool events, and evaluated samples.
  4. Is spend abnormal now? Application counters or the legacy /cost_report at typical ~5m freshness, grouped by workspace where available.
  5. Who owes this month's bill? The Analytics API with ending_at pinned to data_refreshed_at, after reconciliation.
  6. Did a model change cause it? Line behavior history up against deploy timestamps; check stop_reason mix and cache reads first.

Before choosing a threshold, collect: requests per window (a quiet endpoint may need a different alerting approach), the stop_reason distribution, cache-read share, and the plane that produced the number.

Failure modes and recovery

Start by checking whether the alert classified the outcome correctly and whether its data is fresh.

Common mistake Alerting only on HTTP 4xx and 5xx

Refusals, max_tokens truncations, and model_context_window_exceeded stops arrive as HTTP 200 responses carrying stop_reason, and Claude Code logs refusals as claude_code.api_refusal, not claude_code.api_error. Classify each termination by the task: tool_use can be a normal intermediate step, while unhandled truncation may be a failure.

Common mistake Paging in real time on the Analytics API

Analytics data typically refreshes within 4 hours and can take up to 24, and values move until about 7 days after month end. A runaway agent loop can escape timely detection there, and previously reported values can be revised. Page on OTel metrics or the legacy /cost_report; keep the Analytics API for reconciled reports.

Common mistake Treating a dateless 4.6+ ID as a rolling alias

claude-sonnet-4-6 and claude-sonnet-5 are pinned snapshots with fixed weights, so an unexplained behavior change is not a silent upgrade. Router, classifier, and sampling changes can affect behavior on a pinned ID, so compare model IDs and deployments, run regressions, and review transcripts.

Script two recoveries. When cache hit rate falls, confirm with usage.cache_read_input_tokens, then use cache diagnostics to investigate possible prefix changes. Check expiry, traffic, and other possible causes too. When a spend alert fires, read the status code: 400 invalid_request_error is a limit you set and can raise, 429 with enforced_spend_limit_reached requires a higher tier or the next monthly reset, and ramp_limit_exceeded describes the shape of the traffic change, not its level.
