This appendix is a lookup sheet for the Claude Messages API, POST /v1/messages, at anthropic-version: 2026-10-21: headers and transport limits, request and response shapes, content block types, the tool-use turn protocol, structured outputs, SSE streaming, usage accounting, stop reasons versus HTTP errors, model IDs, and beta headers. Endpoint, headers, and transport limits

The Messages API is a single stateless endpoint: POST https://api.anthropic.com/v1/messages serves both single queries and multi-turn conversations, so the application resends the conversation history on every call.

Header Value
Authorization Bearer <api_key_or_wif_token>
anthropic-version 2026-10-21
content-type application/json
anthropic-workspace-id wrkspc_...
anthropic-beta flag1,flag2

The official SDKs send the authentication, version, and content-type headers automatically; you pass anthropic-workspace-id yourself when your key is org-wide rather than scoped to one workspace. Put every beta flag in one comma-separated anthropic-beta header, because Claude Models on Google Cloud (Google managed) reads only one such header and ignores the rest; SDKs expose the same list as betas on the beta client.

Request size caps differ per platform. The first-party API returns HTTP 413 request_too_large when its limit is exceeded.

Platform Request cap
First-party Messages and Token Counting 128 MB
Anthropic-operated cloud platforms 32 MB
Claude Models on Google Cloud (Google managed) 30 MB
Amazon Bedrock 20 MB

Two SDK behaviors matter for long calls. The SDKs reject a non-streaming messages.create() when max_tokens > 21333 as a client-side timeout guard, not an API limit; use client.messages.stream() with stream.get_final_message() in Python, or stream.finalMessage() in TypeScript. The same SDKs retry connection errors, 429, and 5xx twice by default with exponential backoff, honoring retry-after; the count is set by max_retries (maxRetries in TypeScript).

Request body

Sampling parameters are gone: temperature, top_p, and top_k are removed in anthropic-version: 2026-10-21, and sending any value returns 400 on every model.

Field Type Notes
model string Pinned snapshot ID, or a pre-4.6 alias
max_tokens integer Caps thinking plus output tokens
messages array Alternating user, assistant turns
system string or blocks Part of the cached prefix
tools array name plus JSON Schema input_schema
tool_choice object Defaults to auto when tools is set
thinking object adaptive or manual enabled mode
output_config object effort and format
metadata object Opaque user_id only
stream boolean Off by default; true means SSE
cache_control object ephemeral, with ttl of 5m or 1h
speed string standard or fast

max_tokens is a hard ceiling over thinking tokens and visible output together, and setting it to 0 populates the prompt cache without generating a response. messages represents alternating user and assistant turns; consecutive same-role messages in your request are combined into one turn, and each content field is either a string or a block array. Anthropic recommends a UUID, hash, or other opaque identifier for metadata.user_id, which has a maximum length of 512 characters and must not carry a name, email address, or phone number.

Three request shapes return 400 under 2026-10-21: a prefilled final assistant turn on Claude 4.6 or later and on Mythos Preview, with thinking on or off; a document block placed in an assistant message; and non-empty citations in a user message.

The response Message is the generated assistant turn. It returns id (msg_...), type: "message", role: "assistant", model, the content block array, stop_reason, stop_sequence, and usage. In a non-streaming response stop_reason is always non-null.

Content block types

A content block is one typed member of a message's content array. Blocks marked "echo" must be sent back inside the assistant message when you continue a tool-use turn.

type Direction Key fields
text In, out text, optional cache_control, citations
image In: user, tool_result source, optional cache_control
document In: user, tool_result source, optional citations: {enabled}
search_result In: user, tool_result source, title, content
thinking Out, echo thinking text, signature
redacted_thinking Out, echo data
tool_use Out, echo id, name, input
tool_result In: user only tool_use_id, content, is_error
server_tool_use Out, echo id, name, input
web_search_tool_result Out, echo tool_use_id, content

Image blocks accept image/jpeg, image/png, image/gif, and image/webp, and animations are flattened to the first frame. Once a request carries more than 20 images — history turns and images nested in tool_result content included — a stricter per-image dimension limit applies to every image in that request. PDF document blocks allow up to 600 pages per request, or 100 pages when the request's context window is under 1M tokens. A search_result block holds text only: images and other media are not supported inside its content array.

thinking carries readable summary text (empty when display is "omitted") plus the encrypted signature; redacted_thinking carries only encrypted data with no readable text. Both must be passed back to the API unchanged when you continue a multi-turn conversation with tools. tool_use.input is always an object in the finished message even though it streams as string fragments.

Server tools produce two more block types. server_tool_use (ids starting srvtoolu_) records a call Claude ran itself, and web_search_tool_result carries either result blocks — url, title, encrypted_content — or an error block. A failed web search is not an HTTP failure: the API still returns 200, so branch on the block type, and echo encrypted_content unchanged in later turns.

Tool-use turn rules

A tool loop sends tool calls to the application and returns their results to Claude. Message ordering is part of that contract.

  1. The API returns an assistant message whose stop_reason is "tool_use".
  2. Append that assistant content array to messages unchanged, keeping thinking and redacted_thinking blocks in place.
  3. Send one role: "user" message immediately after it; you cannot place any message between the assistant tool_use turn and the tool_result turn.
  4. Put every tool_result block before any text block in that user message.
  5. For parallel calls, return one tool_result for each tool_use block in that single user message, matched by tool_use_id — including an is_error: true result for a call you skipped after an earlier failure.
  6. If the assistant turn also contains a server_tool_use whose result block has not arrived yet, the user message must contain only tool_result blocks: text after the results ends the turn early, and for a server tool Claude called directly the request fails with a 400 naming the unresolved server tool.

tool_choice has these shapes:

tool_choice Effect
{"type": "auto"} Default whenever tools is present
{"type": "any"} Forces at least one tool call
{"type": "tool", "name": "..."} Forces that one tool

Add "disable_parallel_tool_use": true inside the tool_choice object to cap the turn at one call; it is not a top-level request parameter. The two forced forms return 400 under manual extended thinking (thinking.type: "enabled") and are rejected unconditionally on Opus 5.5, Sonnet 5.5, Fable 5.1/5.2, and Mythos 5.1/5.2. Recommended practice in agent loops is therefore tool_choice: {"type": "auto"} paired with strict schemas and explicit prompting, not forced choice.

Common mistake Dropping blocks while filtering history

Code that rebuilds history by keeping "only text and tool_use" deletes redacted_thinking, strips encrypted_content, or reorders tool_result behind text. redacted_thinking must be returned unchanged, tool_result must lead the content array, and encrypted_content must be echoed verbatim.

Worked example: streaming tool loop

The following Python example uses the Anthropic SDK and simulated prices, not live market data. It streams, echoes assistant content, processes client tool calls sequentially, and groups results in one user message. Install a current SDK, configure credentials, and replace the lookup with your own implementation for production.

import anthropic

client = anthropic.Anthropic()  # sends anthropic-version automatically

tools = [
    {
        "name": "get_stock",
        "description": "Return a simulated price for a ticker symbol.",
        "strict": True,
        "input_schema": {
            "type": "object",
            "properties": {"ticker": {"type": "string"}},
            "required": ["ticker"],
            "additionalProperties": False,
        },
    }
]

messages = [{"role": "user", "content": "Compare AAPL and MSFT prices."}]

while True:
    # SDK requires .stream() when max_tokens > 21333; also exposes incremental deltas.
    with client.messages.stream(
        model="claude-sonnet-5-5",
        max_tokens=32000,
        tools=tools,
        tool_choice={"type": "auto"},  # forced "any"/"tool" returns 400 on Sonnet 5.5
        output_config={"effort": "medium"},
        messages=messages,
    ) as stream:
        for event in stream:
            if event.type == "content_block_delta" and event.delta.type == "text_delta":
                print(event.delta.text, end="", flush=True)
        resp = stream.get_final_message()

    # Always echo full assistant content (including thinking / redacted_thinking blocks).
    messages.append({"role": "assistant", "content": resp.content})

    if resp.stop_reason == "tool_use":
        tool_results = []
        for block in resp.content:
            if block.type == "tool_use":
                try:
                    price = {"AAPL": "228.50", "MSFT": "415.10"}[block.input["ticker"]]
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": price,
                    })
                except Exception as exc:
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": f"Lookup failed: {exc}",
                        "is_error": True,
                    })
        # All parallel tool_results go in ONE user message, BEFORE any text.
        messages.append({"role": "user", "content": tool_results})
    elif resp.stop_reason == "pause_turn":
        # Server tool loop paused; re-send the assistant turn with no user message.
        continue
    else:
        print(f"\n[stop={resp.stop_reason} in={resp.usage.input_tokens} out={resp.usage.output_tokens}]")
        break

input_schema, strict tools, and structured outputs

Strict tool use is a per-tool output guarantee set with "strict": true on an individual client tool. Structured outputs is the response-level guarantee, set with output_config: {format: {type: "json_schema", schema: ...}}, which is generally available and needs no beta header. The deprecated top-level output_format parameter only works with anthropic-beta: structured-outputs-2025-11-13, and Python SDK v1.0 or later raises TypeError for a plain dict passed as output_format to client.beta.messages.create() or count_tokens.

A strict schema must set additionalProperties: false on every object, and the compiler rejects recursive schemas, oneOf, not, numeric bounds such as minimum, string length bounds such as minLength, and any other additionalProperties value with a 400. Limits are counted across the sum of all strict tools plus the output schema in one request: at most 20 strict tools, 24 optional (non-required) parameters, and 16 union-type parameters, with an internal grammar size cap and a 180-second compilation timeout; compiled grammars are cached for 24 hours. That is why a request whose strict tools each look simple can still fail to compile.

Three output behaviors need defensive code. Required properties are always emitted before optional ones, whatever order the schema declares. Capitalization of string enum and const values is not guaranteed, so compare case-insensitively. A safety refusal or a max_tokens truncation still returns HTTP 200 and can produce output that violates the schema, so parse and validate only after checking stop_reason; structured output is also incompatible with citations (which returns 400) and with message prefill.

Streaming SSE event sequence

Server-sent events (SSE) deliver a response as a stream of events. With stream: true the sequence is:

  1. message_start — the Message skeleton, with content: [], stop_reason: null, and initial usage.
  2. Per content block, indexed from 0: content_block_start, then zero or more content_block_delta, then content_block_stop for that index.
  3. One or more message_delta events carry top-level changes to the final message; usage counts are cumulative.
  4. message_stop — the terminal event; there is no data: [DONE] sentinel.
  5. Anywhere in the stream: ping keepalives, and error for a failure that arrives after the HTTP 200 headers were sent, for example an overloaded_error.

Delta types inside content_block_delta are text_delta (field text), thinking_delta (field thinking, empty when display is "omitted"), signature_delta (field signature, emitted just before the block stops), input_json_delta (field partial_json), and citations_delta (field citation). Tool arguments stream as partial_json fragments that you accumulate and parse; the final tool_use.input is always an object. Some blocks arrive whole with no deltas at all, including redacted_thinking and server tool results such as web_search_tool_result.

Set eager_input_streaming: true on a tool to skip server-side JSON buffering; it replaces the fine-grained-tool-streaming-2025-05-14 beta. The trade-off is that partial or invalid JSON can reach your client, and a max_tokens stop can cut a parameter mid-value, so guard json.loads() and wait for content_block_stop before executing a side-effecting tool.

Read usage and control fields only from the end of the stream: token counts in message_delta.usage are cumulative, so take the last value rather than summing events, and stop_reason is null in message_start and becomes non-null in later events.

Usage accounting

usage.input_tokens counts non-cached input after the final cache breakpoint, and total input tokens for a request equal input_tokens + cache_creation_input_tokens + cache_read_input_tokens. Prompt caching covers the full prefix in one fixed order — tools, then system, then messages — up to and including the block marked with cache_control. Because that hashing is prefix-based, keep tool definitions and system instructions first with explicit breakpoints, keep thinking mode and output_config.effort constant across turns, and push volatile content such as timestamps and user state to the tail of messages.

usage.server_tool_use reports web_search_requests and web_fetch_requests counters for the turn.

stop_reason versus HTTP errors

stop_reason describes a successful HTTP 200 response; HTTP error statuses describe request-processing failures. Branch on them separately.

stop_reason Meaning Action
"end_turn" Natural completion Use the content
"max_tokens" Hit the ceiling; JSON may be truncated Raise max_tokens or continue
"stop_sequence" Matched one of your stop_sequences Inspect stop_sequence and use the content
"tool_use" Client tool_use block(s) emitted Run tools, reply per ordering rules
"pause_turn" A server-tool loop hit its iteration cap Resume by echoing the assistant turn
"refusal" A classifier intervened; tokens are billed Route to your safety path
"model_context_window_exceeded" Context limit hit before max_tokens Compact history, retry

A "tool_use" stop can arrive alongside an unresolved server_tool_use, which changes the reply shape described above. To resume a "pause_turn", send the assistant content back unchanged (plus container.id if present) with the same tools and no trailing user message. On "refusal", inspect stop_details for the policy category.

Error responses have the shape {"type": "error", "error": {"type", "message"}, "request_id"}.

Status error.type Typical cause
400 invalid_request_error Bad schema, removed sampling parameters, unsupported thinking or tool_choice
401 authentication_error Invalid or expired key
402 billing_error Billing problem
403 permission_error Key lacks permission
404 not_found_error Unknown resource or model
409 conflict_error Conflicting resource state
413 request_too_large Exceeded the platform payload cap
429 rate_limit_error RPM, TPM, or ramp limit; a spend cap can arrive without retry-after
500 api_error Server-side failure
504 timeout_error Request timed out while processing
529 overloaded_error Capacity; may also arrive mid-stream as an SSE error

For transient errors, prefer bounded retries with jittered backoff and honor retry-after when present. Inspect the error first: a spend-cap 429 can persist until access resumes, and a stream error may require recovery of partial output. Branch on stop_reason for completed responses; handle a refusal separately from a length stop.

Editorial decision patterns: distinguish a completed response’s stop reason from an HTTP or stream error. Preserve tool-use blocks and match results by ID. Choose streaming for long calls, and check model and platform support before selecting a beta feature.
